# TL;DR

- 型が不正な状態を許していると、コーディングエージェントはその状態を処理する分岐を律儀に書く。指示が足りないからではなく、型が許した状態を処理しただけなので、**指示を直しても減らない**。
- 増えた分岐の代金は、レビューが払う。到達可能かどうかは型からわからないので、呼び出し元をたどるまで判定できない。2026 年のベンチマークでは、AI 支援の PR は 75 パーセンタイルで 2.6 倍大きく、レビュー着手までの待ち時間は 5 倍以上に伸びている。
- 状態をフラグの組み合わせ（直積）で持つのをやめて判別共用体（直和）にすると、表現できる状態の数が実際に起こる状態の数と一致し、分岐が網羅性検査の対象になる。状態を足したときにコンパイラが修正箇所を列挙するので、それがそのままエージェントへの作業指示になる。
- ただし賢い型は逆効果になる。効くのは型パズルではなく、名前が付いていて局所で読めて、エラーメッセージが直す場所を指す素直な型である。型で書けない規約は lint に落とし、指示に書くのは機械が判定できないものだけにする。

# はじめに

こんにちは、Dress Code でプロダクトエンジニアをしている [ないとー](https://x.com/_bwkw_) です！

私たちは [DRESS CODE](https://www.dress-code.com/ja) という、グローバル向けの Workforce Management プロダクトを開発しています。人事、情報システム、総務、採用、コーポレートなど複数部門を横断する業務 OS として動くコンパウンドプロダクトで、複数の機能が同居し相互に参照し合います。

![事業ドメイン](/images/loose-types-and-dead-branches/business-domain.png)

機能が同居するほど扱う状態の種類は増えていきますが、読み込み中と取得済みと失敗、下書きと申請中と承認済みといった区別を型でどう表すかという判断は、機能を作るたびに出てきます。

この判断が効いてくる範囲は、コードの読みやすさだけではありません。状態の表し方が緩いほど、そのあとに書かれる分岐は増えていきます。

そして、増えた分岐を減らそうとするとき、手が伸びるのは指示の側です。防御的に書くな、不要な分岐を足すな、と伝える方向です。ところが型が `null` を許しているなら、`null` のときの振る舞いを書くのは正しい仕事です。指示で止めにかかっても、正しい仕事をやめさせようとしているだけなので減りません。**変えるべきなのは型の側です。**

以前であれば、これは読みやすさの問題で済んでいました。ところが生成が速くなった今は量の問題になっていて、書く速度が上がった分だけ、差分はレビュー待ちの列に速く、大きな塊で入っていきます。

そして、その分岐が本当に起こるのかを確かめるのは人間です。`if (!data)` と書かれた行を見たとき、それが実際に起こりうる状態への対応なのか、型が緩いせいで書かれただけの死んだ分岐なのかは、呼び出し元をたどって状態の作られ方を確認するまで判断できません。しかも確認した結果はコードのどこにも残らないので、次に同じ関数を読む人が、また同じ作業をやることになります。

書く速度が上がっても読む速度は上がらないのであれば、読む必要のある量そのものを減らすしかありません。型はそれをやる道具で、**型で表現できない状態については、レビューで確かめる作業自体が発生しません**。

そこでこの記事では、生成が速くなった環境で型に何を担わせるべきかを整理します。中心に置くのは判別共用体（discriminated union）で、それを起点に網羅性検査、境界での parse、型で書けない規約を機械に縛らせる話、そして型で表現しないと決めることまで扱います。海外の一次資料を都度示すので、気になったものは原典に当たってもらえると嬉しいです👋

コード例は TypeScript で書きますが、話の中身は静的型付けを持つ言語ならだいたい共通です。

# 速くなったのは実装で、詰まったのはレビュー

「AI で速くなった」という体感は、チーム全体では何を意味しているのでしょうか。

Google Cloud の [2025 年 DORA レポート](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)は、回答者の 90% が業務で AI を使っていると報告しました。この年の結果で目を引くのは、スループット（デリバリーの量）との相関がプラスに転じた一方で、安定性（変更失敗率などの指標）との相関は依然としてマイナスのままだったところです。同レポートはこれを、AI がチームを直すのではなくすでにあるものを増幅すると要約していて、自動テストや速いフィードバックループといった制御装置を欠いたまま変更量が増えれば、それが不安定さとして表に出てくるという説明になっています。

その増幅がどこに現れるかを細かい粒度で示したのが、[LinearB の 2026 年 Software Engineering Benchmarks Report](https://linearb.io/resources/software-engineering-benchmarks-report) です。810 万件の PR を分析したこのレポートでは、AI 支援の PR は 75 パーセンタイルで 408 行と、支援なしの 157 行に対して 2.6 倍の大きさになっていました。さらに、エージェントが生成した PR がレビューに着手されるまでの待ち時間は、支援なしの PR の 5 倍以上に伸びています。

その待ち時間の中身は、[Stack Overflow の 2025 年 Developer Survey](https://survey.stackoverflow.co/2025/ai) が示しています。33,662 人の回答のうち、AI に対する最大の不満は「ほぼ正しいが、少しだけ違う解答」で 66%、2 位が「AI が生成したコードのデバッグに時間がかかる」の 45.2% でした。明確に壊れているコードは問題になりません。**動いてしまうが少し違うコードが、人間の時間を食います**。

コードそのものの形も変わってきています。GitClear の [2026 年 The Maintainability Gap](https://www.gitclear.com/the_ai_code_quality_maintainability_gap) は 2023 年から 2026 年の 6.23 億件の変更を分析し、リファクタリングを示す「移動された行」の比率が 2022 年の 21% から 2026 年の 3.8% まで落ちたと報告しました。この記事の関心から特に重要なのは、エラーを覆い隠す構文（例外の握り潰しや暗黙のフォールバック）が 47% 増えたという指標で、生成されたコードは扱いに困る状態を黙って飲み込む方向に寄っています。

であれば、設計で狙うべき効果もはっきりします。差分を読まずに済ませられる範囲を広げることです。テストは「書いた振る舞いが壊れていない」ことを教えてくれますが、書かれていない状態については何も言いません。型が引き受けられるのはこちら側で、表現できない状態は最初から検討の対象になりません。

# 緩い型は、ハンドリングを書かせる

具体例から入ります。従業員の一覧を取得して表示する画面の状態を、素直に書くとこうなります。

```typescript
type EmployeeListState = {
  isLoading: boolean;
  employees: Employee[] | null;
  error: Error | null;
};
```

この型が表現できる状態の数を数えてみると、`isLoading` が 2 通り、`employees` が「配列か `null`」で 2 通り（要素数は無視します）、`error` も 2 通りなので、掛け合わせて 8 通りになります。型が表現できる値の個数は、集合論の言葉で cardinality と呼ばれます。Scott Wlaschin はこれを型の「サイズ」と呼び替えて、ドメインモデリングの道具として整理しています。

https://fsharpforfunandprofit.com/posts/type-size-and-design/

一方、実際に起こる状態は 4 つしかありません。まだ読み込んでいない状態と、読み込み中、成功、失敗の 4 つです。差の 4 通りは、`isLoading` が真なのに `error` が入っている状態や、成功と失敗のどちらでもないのにデータが空の状態です。どれも意味を与えていない組み合わせで、仕様に存在しないだけで型としては合法です。

この型を前提に描画関数を書くと、こういう形になります。

```tsx
function EmployeeList({ state }: { state: EmployeeListState }) {
  if (state.isLoading) return <Spinner />;
  if (state.error) return <ErrorPanel error={state.error} />;
  if (!state.employees) return <EmptyPlaceholder />;
  if (state.employees.length === 0) return <EmptyPlaceholder />;
  return <List employees={state.employees} />;
}
```

`!state.employees` の分岐と `state.employees.length === 0` の分岐は、どちらも同じ `EmptyPlaceholder` を返していますが、意味は違います。後者の「取得に成功したが 0 件だった」は仕様上ありますし、前者の「読み込み中でもエラーでもないのにデータが無い」は仕様上存在しません。それでも `employees` が `null` になりうると型が言っているので、書き手はその分岐を埋めます。指示が足りないから書かれたのではなく、**型が許した状態を処理しただけで、むしろ真面目な振る舞いです**。

人間が書くなら、ここは違う結果になることもあります。「この状態は来ないはず」と判断して分岐を書かずに済ませる余地があるからですが、エージェントはその判断をせず、型が許した状態を処理すべき状態として扱います。エージェント向けの設計パターンを集めた Encyclopedia of Agentic Coding Patterns も、同じ観察を書いています。型が不正な状態を許せばエージェントはその状態を扱うコード（分岐、検証、例外送出）を書き、型を締めれば考慮すべき場合が減るので出力が単純になる、というものです。

https://aipatternbook.com/make-illegal-states-unrepresentable

レビュー側から見て厄介なのは、前者が死んだ分岐だとコードを読んだだけでは判定できないところです。判定するには、`isLoading` が偽で `error` が無く `employees` が `null` になる経路が無いことを、状態を作っている場所すべてで確認する必要があります。

この構造は Robert Harper が 2011 年に **boolean blindness** として書いたものです。真偽値は値以外の情報を運ばないので、それで分岐した瞬間に、何を検査したのかという情報が失われます。`isLoading` という名前は変数名に残っていますが、`true` という値自体は「読み込み中である」という事実を持っていません。フラグを 3 つ並べた型は、この情報の欠落を 3 重に重ねた状態になります。

https://existentialtype.wordpress.com/2011/03/15/boolean-blindness/

代わりに、起こりうる状態をそのまま直和で並べます。

```typescript
type EmployeeListState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "loaded"; employees: Employee[] }
  | { status: "failed"; error: Error };
```

表現できる状態の数は 4 通りになり、実際に起こる状態の数と一致しました。`status` という共通のタグで判別できるので、TypeScript はタグを見た分岐の中で残りのフィールドを絞り込みます。これが **判別共用体** です。

この型を前提に同じ関数を書くと、こうなります。

```tsx
function EmployeeList({ state }: { state: EmployeeListState }) {
  switch (state.status) {
    case "idle":
      return <Placeholder />;
    case "loading":
      return <Spinner />;
    case "loaded":
      return state.employees.length === 0 ? (
        <EmptyPlaceholder />
      ) : (
        <List employees={state.employees} />
      );
    case "failed":
      return <ErrorPanel error={state.error} />;
  }
}
```

今度は、死んだ分岐を書く余地がありません。`error` は `failed` の中にしか存在しないので成功時にエラーを参照するコードは型エラーになりますし、`employees` も `loaded` の中にしかないので `null` チェックを書く理由がありません。レビュアーが見るのは 4 つの分岐がそれぞれ妥当かどうかだけで、**状態の作られ方を追う作業は型定義を読んだ時点で終わっています**。

この設計は、Yaron Minsky の言葉を借りて「不正な状態を表現できなくする」として知られていて、Scott Wlaschin が実務向けに詳しく展開しています。AI とは無関係な時代の議論ですが、生成量が増えた環境では効果の出方が変わります。以前は「防御的な分岐が減って読みやすい」という程度の利点でしたが、今は書かれる分岐の総量が減るという、量に効く利点になりました。

https://fsharpforfunandprofit.com/posts/designing-with-types-making-illegal-states-unrepresentable/

# 網羅性検査が、修正箇所の一覧を作ってくれる

判別共用体のもう半分の価値は、状態を足したときに現れます。たとえば一覧の再読み込み中に古いデータを表示したくなって、状態を 1 つ追加したとします。

```typescript
type EmployeeListState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "loaded"; employees: Employee[] }
  | { status: "refreshing"; employees: Employee[] }
  | { status: "failed"; error: Error };
```

戻り値の型が宣言されているか `noImplicitReturns` が有効なら、この変更だけで `switch` を書いた全箇所が型エラーになり、そのエラーの一覧がそのまま修正すべき場所の一覧になります。フラグ 3 つの型では、`isRefreshing` を足しても既存のコードは全部コンパイルを通るので、どこを直すべきかは誰も教えてくれません。動かしてみて古いデータが消えることに気づくまで、この漏れは表に出てきません。

これは生成が速い環境でとりわけ効きます。「状態を 1 つ足して」と頼んだとき、型定義だけ書き換えて呼び出し側を直し忘れるのはエージェントがよくやる失敗ですが、網羅性検査があれば直し忘れた箇所は型エラーとして機械が指摘するので、**そのメッセージを渡すだけで作業が終わります**。

ただし、この保証は簡単に殺せます。`default` 節を書いた瞬間に新しい状態は既存の `default` に吸収され、コンパイラは何も言わなくなるので、保証を残したいなら到達しないことを型で表明する形にします。

```typescript
function assertNever(value: never): never {
  throw new Error(`unexpected variant: ${JSON.stringify(value)}`);
}

function label(state: EmployeeListState): string {
  switch (state.status) {
    case "idle":
      return "未取得";
    case "loading":
      return "読み込み中";
    case "loaded":
      return "取得済み";
    case "failed":
      return "取得失敗";
    default:
      return assertNever(state);
  }
}
```

`refreshing` を追加すると `assertNever(state)` の引数が `never` に収まらなくなり、この行が型エラーになります。`default` 節を持ちながら網羅性を保つ書き方で、レビューのチェック項目としては「判別共用体に対する `switch` に素の `default` が書かれていないか」を見るだけで済みます。

判別共用体をネイティブに持たない言語でも、同じ効果はだいたい作れます。Java や Kotlin の `sealed class`、Rust の `enum`、Python の `Literal` を使ったユニオンが、それぞれの答えになります。PHP のように後付けの言語でも、`enum` と `match`、あるいは `interface` を `@phpstan-sealed` で閉じることで同程度のことはできます。必要なのは言語機能の名前ではなく、状態の集合を型で閉じて分岐漏れを機械に見つけさせる形です。

# 境界で型を確定させる

もう 1 つ、生成量が増えた環境で効く型の使い方があります。検証済みという事実を型で運ぶことです。

出発点は Alexis King の "Parse, don't validate" です。入力を検査して真偽値を返す関数（validate）を書くと検査した事実は呼び出し元に残りませんが、検査を通ったことが型に現れる値を返す関数（parse）を書けば、その事実は型として先に運ばれます。

https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/

事実が運ばれないと何が起きるかは、引数の型を見れば分かります。

```typescript
function sendInvite(email: string) {
  if (!email.includes("@")) throw new Error("invalid email");
  // 送信処理
}
```

この関数の作者は `email` が検証済みかどうかを知らないので、自分で検査します。同じ引数を受け取る関数が 10 個あれば、同じ検査が 10 箇所に書かれます。しかも書き方は毎回少し違って、ある関数は例外を投げ、別の関数は黙って早期 return します。GitClear が報告したエラーを覆い隠す構文の増加は、この問いに毎回その場で答えた結果の集積だと考えると筋が通ります。

境界で一度 parse して、以降は確定した型で受け渡します。

```typescript
declare const brand: unique symbol;
type Branded<T, B extends string> = T & { readonly [brand]: B };

type EmailAddress = Branded<string, "EmailAddress">;

function parseEmailAddress(raw: string): EmailAddress | null {
  const trimmed = raw.trim();
  return /^[^@\s]+@[^@\s]+$/.test(trimmed) ? (trimmed as EmailAddress) : null;
}

function sendInvite(email: EmailAddress) {
  // 送信処理
}
```

`sendInvite` が検査を書かないのは、書く理由がないからです。これが効くのは緩い型がエージェントに分岐を書かせるのと同じ理屈です。引数の型が `string` なら「@ が無かったらどうする」を考えて防御を書きますが、`EmailAddress` ならその問いは発生しません。

どこまで型で受け取るかの指針としては、Matt Parsons の "Type Safety Back and Forth" が分かりやすい整理を与えてくれます。失敗しうる処理の安全性は、2 方向に押し出せます。前に押し出すなら戻り値を `Either` や `Maybe` のような型にして、呼び出し側に失敗の処理を担わせます。後ろに押し出すなら `NonZero` のような型を引数に要求して、呼び出し側に正しい入力の用意を担わせます。

https://www.parsonsmatt.org/2017/10/11/type_safety_back_and_forth.html

この 2 択は、レビューの量に対して逆向きに働きます。前に押し出すと呼び出し箇所の数だけハンドリングが増え、後ろに押し出すと値を作る場所へ検査が集まります。値を作る場所は普通、使う場所よりずっと少ないので、ドメインの内側では後ろに押し出す方が読む量は減ります。一方、外部入力を受け取る境界では、外の世界が型を守ってくれる保証がないので、失敗を前に押し出すしかありません。

ここで 1 つ注意があります。型に名前を付けただけでは、保証は生まれません。Alexis King は "Names are not type safety" で、newtype でラップしただけの型と状態を直和で構成した型の差を論じています。ラッパは、そこを通れば値が正しいという規約をコードの外に置いているだけで、下流の関数は結局元の型を受け取っているのと同じです。決定的な差は変更時に出て、直和で構成した型に選択肢を足せば網羅していない分岐がコンパイル時に検出されますが、ラッパの中身に新しい形式を足してもコードは通り、実行時に落ちます。

https://lexi-lambda.github.io/blog/2020/11/01/names-are-not-type-safety/

**branded type は、コンストラクタを閉じたときにだけ意味を持ちます**。上の例で言えば、`parseEmailAddress` 以外の場所で `as EmailAddress` を書けるなら、この型は名前でしかありません。まず状態を直和で表せないかを考えて、値の制約として表すしかないものだけを parse 関数に回す、という順番が良いと思います。

# 賢い型は、かえって足を引っ張る

ここまで読むと、型を厳しくすればするほど良いという結論に見えるかもしれません。ところが、生成が速い環境ではそうなりません。

Armin Ronacher は "In Support Of Shitty Types" で、エージェントと型システムの相性について直感に反する観察を報告しています。型チェックをエージェントのループに入れると、彼のテストではむしろ性能が落ちました。エージェントはまずコードを書き、あとから型エラーを見つけ、その解消にコンテキストを費やすからです。TypeScript の込み入った型レベルの機能や、それを駆使したライブラリについては、モデルはそもそも読み方をわかっていないとも述べています。

彼が挙げるモデルにとって重要な性質は具体的で、型を完全に理解する必要はなく、ある値がおおよそ何の型かが分かればよいというものです。それよりも、エラーメッセージに出てくる型名がソースの型名と一致していることの方が大事だと言います。だから Go のように表現力の低い型システムの方が、モデルにとってはうまく機能する、と続きます。

https://lucumr.pocoo.org/2025/8/4/shitty-types/

翌年の "A Language For Agents" では、この観察が言語設計への要求として整理されています。型推論で記述量を削るよりも明示的に書いた方がエージェントには有利で、LSP を立てなくてもファイルを読めば型がわかる方がよく、名前で grep できるかどうかも効いてきます。エージェントは数ファイルしかコンテキストに載せないため、離れた場所に情報が隠れていない構造を好みます。彼はこれを **local reasoning** と呼んでいます。

https://lucumr.pocoo.org/2026/2/9/a-language-for-agents/

この 2 本を、前の節までの議論への反論として読むと筋を見失います。Ronacher が使えないと言っているのは型による不変条件の表明そのものではなく、条件型や深いジェネリクスのように、型の意味が定義から離れた場所で計算される機構です。彼が有利だと言っているのは、明示的で、局所で読めて、エラーが直す場所を指す型です。

そう読むと、効く型の条件が絞れます。名前が付いていて、定義が 1 箇所にまとまっていてその場で読めて、その名前で grep でき、違反したときのエラーメッセージが直すべき場所と直し方を指していることです。

判別共用体はこの条件を全部満たします。定義は数行で、状態の名前がそのままコードに出て、`status` で grep でき、分岐漏れのエラーは「この `switch` にこのケースが無い」という直し方まで含んだ形で出ます。一方、条件型で状態の整合性を表現した型はどれも満たしません。エラーメッセージは展開後の巨大な型を吐き、直す場所は型の定義側にも使用側にも見えます。**人間が読むのにも苦労するものを、エージェントが読めるはずもありません**。

型が生成そのものを助けるという方向の証拠もあります。Niels Mündler らの "Type-Constrained Code Generation with Language Models" は型システムを使って生成をデコード時に制約する手法を提案し、コンパイルエラーを半分以下に減らしています。使っているのは型が生成の探索空間を機械的に絞れるという性質で、その絞る力は型が単純で機械的に扱えるほど素直に働きます。

https://arxiv.org/abs/2504.09246

AI 時代に価値が上がったのは、賢い型ではなく素直な型です。設計の努力を注ぐ先は型レベルプログラミングの高度化ではなく、状態を直和で並べ直すことと、境界で parse することの側にあります。

# 型で書けない規約は、機械に縛らせる

ここまでで、型に書ける制約と型では書けない規約が分かれてきました。後者として残っているのは、判別共用体に対する `switch` に素の `default` を書かないことと、branded type への `as` を parse 関数の中だけで使うことです。どちらも守られていれば保証が成立し、破られた瞬間に保証が消えます。

この種の規約をレビューの観点として人間の頭に置いておくのは、差分の量に比例して見落としが増えるので、生成量が増えた環境では割に合いません。守らせたいなら、機械が落とす形にします。

`default` の方は既存のルールがそのまま使えます。typescript-eslint の `switch-exhaustiveness-check` は、リテラルのユニオンや `enum` に対する `switch` で、ケースが欠けていると報告するルールです。型情報を使うので実行コストはかかりますが、`allowDefaultCaseForExhaustiveSwitch` を `false` にすれば、網羅済みの `switch` に `default` を書くこと自体を禁止できます。`assertNever` を挟む書き方を強制するなら、この設定が一番手軽です。

https://typescript-eslint.io/rules/switch-exhaustiveness-check/

`as` の制限は既存ルールだけでは足りないので、`no-restricted-syntax` で型アサーションそのものを撃つか、ブランド型とその parse 関数を 1 つのモジュールに閉じて外から生の値を渡せない形にするかになります。どちらにしても、規約が壊れたことを機械が指摘する状態には持ち込めます。

そのうえで、エージェントへの指示（スキルや CLAUDE.md のような形）に書くのは、機械が落とせないものだけにします。自然言語の指示は確率的にしか効かないので、決定的に判定できることを指示で担保するのは無駄です。逆に、lint に落とせない判断は指示に書く価値があって、「状態はフラグの組み合わせではなく判別共用体で表す」「外部入力は境界で parse して内側には確定した型だけを流す」といった設計方針は、機械には判定できませんが生成の時点で効きます。

制約の置き場所については、Armin Ronacher が的確な指摘をしています。権限チェックを別のファイルや設定に隠すと、AI はほぼ確実にそれを追加し忘れるというものです。**制約は、それが必要な場所の近くに置くか、機械が場所を指して落とすかのどちらかにしないと守られません**。

https://lucumr.pocoo.org/2025/6/12/agentic-coding/

降ろし方には順番があります。型で表現できるものは型に置き、型では書けないが機械的に判定できるものは lint に、判定できない設計判断だけをスキルに降ろします。この順で降ろすほど、エージェントが書かずに済むコードが増えていきます。なお、前の節で触れた「型チェックをループに入れると性能が落ちた」という観察は、生成の途中で型チェックを回すことについての話で、コミット前や CI で落とす仕組みを否定するものではありません。

# 型で表現しないと決める

最後に、型に押し込まないという判断について書きます。ここを決めずに始めると、途中で型が目的になります。

Rich Hickey は "Maybe Not" で、`Maybe` を含む型システムの扱い方に反論しました。彼の指摘の中心は、データの形（`string` である）とデータの供給（必須である）は別の考えなのに、型システムがその 2 つを一緒に持たせることを強いる点にあります。

https://www.youtube.com/watch?v=YR5WdGrpoug

この反論は、状態の直和化とは違うレイヤーの話です。ある画面の状態が 4 つのどれかであるという事実は、そのドメインに固有の性質です。型に書いて損はありません。一方、あるフィールドが必須かどうかは文脈によって変わり、作成時には未確定でよく承認時には必須になるフィールドは珍しくありません。これを 1 つの型で省略可能なフィールドとして書くと、どの文脈でも `null` チェックが要る型が出来上がります。文脈ごとに型を分けるのが素直な答えで、状態ごとにデータを持たせる判別共用体はまさにそれをやっています。

もう 1 つの線引きは、型が届かない場所を認めることです。型はプロセスの境界を越えると失われるので、データベースの nullable なカラムや外部 API の JSON、CSV の 1 行から入ってくる値は、こちらの型が何を宣言していようと関係なく到着します。だから境界に parse を置く必要があり、境界の内側だけが型の保証範囲になります。

そして、静的な型では表せない条件があります。Alexis King 自身が、"Parse, don't validate" は書こうとしている関数の必要から型の表現を決める話だと補足したうえで、「配送可能なメールアドレス」のような性質はどんな静的型でも捉えられないと述べています。形式が正しいことは parse できますが、そのアドレスが実在して受信できることは送ってみるまで分かりません。この種の条件は実行時の検査と運用で扱うしかなく、型で表現しようとすると嘘の保証を作ることになります。

線引きの目安として、私は次の順で考えています。起こりうる状態が数えられるなら直和で並べ、値の制約が形式として書けるなら境界で parse して型に持たせます。ここまではコストがほぼ設計の手間だけなので、やる価値がほぼ常にあります。その先、状態遷移の順序を型で強制する手法まで行くかは、間違えたときの損害で判断します。決済や権限のように順序を間違えると取り返しがつかない領域では見合いますが、画面の表示状態のために型パラメータを増やすのは高くつきます。

https://cliffle.com/blog/rust-typestate/

# おわりに

生成が速くなって変わったのは、コードを書く速さだけではありませんでした。緩い型を放置したときの請求書が、以前よりずっと早く、大きな額で届くようになります。型が許した状態は分岐として埋められ、その分岐が生きているのか死んでいるのかを 1 つずつ確かめるのは、結局のところ人間です。

だからこそ、型でやれることを型でやっておく価値が上がりました。判別共用体で状態を並べ直すのは数行の書き換えですが、それだけで書かれずに済む分岐と読まずに済む差分が増えます。派手な手法ではありませんが、生成が速くなるほど効き方が大きくなる種類の設計だと思っています。

型で状態を締めるところから始めてみると、レビューで確かめる項目が減っていくのを実感できるはずです。読む量を減らす設計の 1 つとして、参考になれば幸いです👋
