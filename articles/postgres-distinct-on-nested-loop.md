# まず、クエリの外側を疑った

重い集計クエリと聞くと、つい SQL チューニングに手が伸びます。私も最初はそうでした。今回は在籍2,000人ほどのテナントで計測していて、この就業形態カードは約7.3秒かかっていました。ところがコードを並べてみると、律速していたのは SQL 単体ではありませんでした。

## 件数が欲しいのに、全行を取って JS で数えていた

必要なのは就業形態ごとの人数、つまりほんの数個の整数です。ところが実装は、全件分の表示用オブジェクトをいったん取得してから、アプリ側で数え上げていました。

```typescript
// before: 全件を取得して、アプリで就業形態ごとに filter().length
const workers = await fetchWorkers(orgId); // 数千〜十数万行が返ってくる
return {
  employee: workers.filter((w) => w.workerType === "EMPLOYEE").length,
  contractor: workers.filter((w) => w.workerType === "CONTRACTOR").length,
  // ...種別の数だけ繰り返す
};

// after: DB で数える。返ってくるのは種別ごとの1行ずつ
// SELECT worker_type, count(*) FROM (...スナップショット...) GROUP BY worker_type
return await countByWorkerType(orgId); // 数行が返ってくる
```

やったことは単純で、数千〜十数万行を組み立てて転送し、メモリ上で `filter().length` していた処理を、`COUNT` + `GROUP BY` に置き換えて DB に任せただけです。取得元もフィルタも種別判定のロジックも変えていないので、出てくる件数は同じです。あわせて、このクエリは件数には要らない一覧表示用の重い列まで毎回作っていたので、件数だけが欲しいときはそこを計算しないようにしました。

## 独立した集計を、直列で待っていた

そして、いちばん効いたのは呼び出し方でした。このカードは今月時点と先月時点の2回ぶんを集計するのですが、その2回を直列に `await` していたのです。互いに依存しない読み取りなのに、実行時間がそのまま足し算になっていました。独立しているなら並列に投げればよく、待ち時間はいちばん遅い1本ぶんに縮みます。

```typescript
// before: 独立した集計を直列 await（実行時間が単純加算される）
const current = await countByWorkerType(currentDate);
const lastMonth = await countByWorkerType(lastMonthDate);

// after: 独立 read なので並列化（待ちは「いちばん遅い1本」に縮む）
const [current, lastMonth] = await Promise.all([
  countByWorkerType(currentDate),
  countByWorkerType(lastMonthDate),
]);
```

ただ、並列化には落とし穴があります。1本のコネクションは、同時に1つのクエリしか実行できません。

:::message
これは特定のライブラリ固有の話というより、PostgreSQL のコネクションが同時に1クエリしか扱えないことに由来します。私たちは Prisma を使っていますが、そのインタラクティブトランザクション（`$transaction`）は1本のコネクションに固定されます。すると、同じトランザクション内のクエリを `Promise.all` で束ねても、下で動く `pg`（node-postgres）が先入れ先出しで直列に流すだけです。`pg` のバージョンによっては `client.query() ... is already executing a query` という警告も出ます。並列が効くのは、コネクションを共有しない独立した読み取り、たとえばプールや Read Replica のように別コネクションを使う場合に限られます。つまり、同じトランザクションの中は直列、独立した読み取りだけが並列、というのが境目でした。
:::

https://node-postgres.com/features/pooling

この2つ、DB 集計と並列化だけで、就業形態別のカードは 7.3秒から 1.8秒へ、およそ4倍速くなりました。しかも SQL は一文字も賢くしていません。1本のクエリを速くしにかかる前に、まずそのクエリが何回・どんな順序で呼ばれているかを見るのが先です。直列の `await` や N+1 といった呼び出し方の問題は、SQL 自体をチューニングするより桁で効くことがよくあります。

# 次に、`EXPLAIN` でクエリ本体を覗く

外側を削ると、今度はクエリ自体の遅さが顔を出します。`EXPLAIN ANALYZE` を覗くと、犯人ははっきりしていました（実際のプランからの抜粋です）。

```text
->  Nested Loop  (actual rows=2180 loops=1)
      ->  Unique  (cost=... rows=200 ...) (actual rows=167766 loops=1)   -- DISTINCT ON サブクエリ
            ->  Sort (rows=168077 ...)  Sort Method: external merge  Disk: 12872kB
      ->  Index Only Scan using idx_worker_org_person on worker  (rows=1) (actual rows=0.01 loops=167766)
            Index Cond: ((organization_id = '...') AND (person_id = "*SELECT* 1".person_id))
```

注目すべきは、`rows=`（プランナの見積り）と `actual rows=`（実測）のギャップです。プランナは `DISTINCT ON` のサブクエリ（`Unique`）の出力を 200 行と見積もっていますが、実測は 167,766 行。約840倍の過小見積りでした。この `DISTINCT ON` は契約や協力者を広く集めてから1人1件に絞り込む中間処理なので、出力はこのカードが最終的に数える人数より大きくなります。`EXPLAIN` の各列の読み方は、公式ドキュメントが詳しいです。

https://www.postgresql.org/docs/current/using-explain.html

この過小見積りが、結合方式の選択をそのまま歪めます。nested loop のコストは、ざっくり言えば「外側の行数 × 内側を1回引くコスト」です。外側が 200 行なら、内側をインデックスで1件ずつ引く nested loop がいちばん安く見えます。

ところが現実の外側は約17万行でした。そのため、サブクエリの各行について在籍者テーブルをインデックスで引く処理が `loops=167766`、つまり約17万回も繰り返されていたのです。1回の探索がいくら速くても、約17万回まわれば効いてきます。

nested loop のこの性質は、Use The Index, Luke! の解説が分かりやすいです。

https://use-the-index-luke.com/sql/join/nested-loops-join-n1-problem

では、約17万行どうしをつなぐなら何が向いていたのか。こういうときは、1行ずつ引くのをやめて、両者をまとめて突き合わせる方式（hash join や merge join）が向きます。たとえば hash join は、片方をいったんメモリ上のハッシュ表に展開し、もう片方をそれに当てていく方式で、それぞれを1回スキャンするだけで済みます。表を作るコストはかかりますが、行数が増えても「両方の行数の足し算」くらいで頭打ちになります。対して nested loop は「外側の行数 × 内側1回ぶん」で、外側に比例して回数が膨らむ。つまり外側が小さいうちは nested loop が安く、大きくなるとまとめて突き合わせる方式が逆転する、という関係です。今回プランナが nested loop を選んだのは外側を 200 行と読み違えていたからで、本当の約17万行が見えていれば、別の方式のほうが安いと判断できたはずでした。

## なぜ `200` なのか — `DEFAULT_NUM_DISTINCT`

そもそも、なぜ 200 などというキリのいい数字が出てくるのか。これは偶然ではありませんでした。

問題のクエリは、人員のスナップショットを組み立てるために、`DISTINCT ON` を使ったサブクエリを抱えていました。1人につき有効な契約を1件に畳み込むもので、このあと `unified_contract` と呼びます（`EXPLAIN` に出てくる `"*SELECT* 1"` は、このサブクエリの中の SELECT に付くプランナ内部の名前です）。簡略化すると、こんな形です。

```sql
-- 1人につき「いま有効な契約」を優先度順に1つだけ選ぶ
SELECT DISTINCT ON (person_id) *
FROM (
  SELECT ... FROM contract_a WHERE ...
  UNION ALL
  SELECT ... FROM collaborator WHERE ...
) AS unified_contract
ORDER BY person_id, priority_score DESC, valid_from DESC
```

ポイントは、統計の有無です。実テーブルのカラムには統計がありますが、`DISTINCT ON` や `GROUP BY`、サブクエリの出力には統計がありません。だからプランナは、サブクエリが吐く `person_id` が何種類あるのかを知るすべがないのです。

統計が引けないとき、プランナがどう動くかを追ってみます。`DISTINCT ON (person_id)` の出力行数は、`person_id` が何種類あるかに等しいので、プランナはまずその種類数を見積もろうとします。`GROUP BY` のグループ数を見積もるのと同じ仕組みです。

ところが、その種類数を引こうとした列は、実テーブルではなくサブクエリの出力でした。実テーブルなら統計テーブル（`pg_statistic`）から読めますが、サブクエリの出力にはそれがありません。手がかりが尽きると、PostgreSQL は分からないという印をつけ、ソースに直書きされた既定値を返します。それが `selfuncs.h` の `DEFAULT_NUM_DISTINCT`、すなわち 200 です。

https://github.com/postgres/postgres/blob/d424d06ed2d6c6f0f11c515248a9b22e8d1a794a/src/include/utils/selfuncs.h#L52

これが `rows=200` の正体で、種類数が分からないのでひとまず 200 としておく、というプランナの白旗だったわけです。

厄介なのは、その白旗の 200 が結合方式の選択まで動かしてしまう点です。プランナは与えられた前提の中ではいちばん安いプランを正直に選んでいますが、その前提が約840倍ずれている。誤推定はコストモデルの外側から効いてくるので、まず `EXPLAIN ANALYZE` で `rows`（見積り）と `actual rows`（実測）の比を見るのが定石になります。

これは PostgreSQL のバグではなく、派生リレーションの出力には統計がないという、構造的な性質です。

## 王道を順に潰す

ここまでで、遅さの正体が、誤推定に駆動された nested loop だと見えてきました。とはいえ、いきなり nested loop を無理やり別の方式へ切り替えにいくのは第一選択ではありません。まずはプランナが自分で正しいプランを選べるよう、王道から当てていきます。が、今回はことごとく外れました。

- 結合キーにインデックスを足す → 1回ごとの探索は、すでにインデックスで十分速い。遅いのは1回が遅いからではなく、その速い探索が約17万回も繰り返されるから。問題は回数のほうなので、インデックスを足しても変わらない。
- 統計を更新する（`ANALYZE`）→ 統計は健全で、そもそも前述のとおりサブクエリの出力には付けられる統計がない。
- 拡張統計（`CREATE STATISTICS`）→ 列どうしの相関には効くが、対象は実テーブルのカラムで、派生リレーションには付けられない。
- `MATERIALIZED` な CTE で実体化する → 実体化はしてくれるものの、その出力に対する上位の見積りは直らず、結局は同じ場所で倒れる。

最後の手段が `SET LOCAL enable_nestloop = off` です。たしかに nested loop を止められますが、[公式ドキュメント](https://www.postgresql.org/docs/current/runtime-config-query.html#RUNTIME-CONFIG-QUERY-ENABLE)もこの種のフラグを一時しのぎと位置づけ、まずは `ANALYZE` やコスト定数、統計の調整を勧めています。実際これはプランナの判断を上書きしているだけで、真因である推定誤りは残ったままです。同じクエリの別の場所で、いつかまた別の nested loop が顔を出すかもしれません。できれば、プランナが自然に良いプランを選べる形に、クエリ側を持っていきたいところです。

# その列、本当に「結合で」取り出す必要がある？

そこで、視点を変えてみました。

遅さの引き金は、就業形態を導出する LEFT JOIN でした。従業員・役員・業務委託（テーブルでいう `employee` / `board_member` / `contractor`）という種別ごとのテーブルを結合し、どのテーブルに記録があるかで種別を決めていたのです。整理すると、集計で種別の列を参照しているためにプランナはこの結合を外せず、相手が例の「200 行と読み違えたサブクエリ」なので、その誤りに引きずられて nested loop へ倒れていたわけです。

ならば、その列を結合で取ってくること自体をやめてみればいい。就業形態は、突き詰めれば、その契約が従業員にあたるかどうか（従業員テーブルに記録があるか）を確かめるためにしか使っていません。だとすれば、列として取り出すのではなく、存在判定（`EXISTS`）として書けます。そこで集計クエリの `FROM` から種別テーブルの結合を外し、就業形態を `EXISTS` で判定する CASE 式に置き換えました。

```sql
CASE
  WHEN EXISTS (SELECT 1 FROM employee e
               WHERE e.worker_contract_id = unified_contract.contract_id
                 AND e.employment_type_id IS NOT NULL) THEN 'EMPLOYEE'
  WHEN EXISTS (SELECT 1 FROM board_member b WHERE ...) THEN 'BOARD_MEMBER'
  WHEN EXISTS (SELECT 1 FROM contractor  c WHERE ...) THEN 'CONTRACTOR'
  ...
END
```

この状態で `EXPLAIN` を取り直すと、プランは次のように変わっていました。

```text
->  Merge Left Join  (actual rows=2182)
      Merge Cond: (worker.person_id = "*SELECT* 1".person_id)
      ->  Index Only Scan using idx_worker_org_person on worker  (actual rows=2182)   -- org で先に絞って駆動表に
      ->  Unique  (rows=200) (actual rows=167692)                                      -- 畳み込みは残るが、もう駆動表ではない
SubPlan 1  ->  Index Only Scan using employee_pkey on employee e        (loops=1509)
SubPlan 2  ->  Index Only Scan using board_member_pkey on board_member b (loops=89)
SubPlan 4  ->  Index Only Scan using contractor_pkey on contractor c     (loops=72)
```

まず変わったのは、駆動表（結合の起点になるテーブル）です。在籍者テーブルを先に組織で絞り込み（`idx_worker_org_person` で 2,182 行）、それを起点にサブクエリと結合するようになりました。行数を 200 と読み違えたサブクエリは、もう nested loop の起点ではありません。そして種別の判定は、本体の結合から外れて、`EXISTS` ごとの SubPlan、つまり親プランにぶら下がる小さな子プランになっています。

本体の結合は、まさに先ほどの「まとめて突き合わせる方式」、ここでは `Merge Left Join` になりました。在籍者テーブルを `person_id` 順のインデックスでそのまま読めるので、ソート済みどうしを突き合わせる merge join が選ばれています。狙いは特定の方式に寄せることではなく、誤推定のサブクエリを駆動表から外すこと。そこさえ解ければ、あとの方式選びはプランナに任せられます。

この一手で、`Buffers: shared hit` は 580,431 から 42,231 へ、およそ14分の1になりました。効いたのは、約17万回の在籍者テーブル探索が消えたことです。改善前はサブクエリの約17万行それぞれについて在籍者テーブルを引いていて、そのインデックス探索だけで約50万 buffers を使っていました。改善後は先に在籍者テーブルを 2,182 行へ絞ってから結合するので、その無駄打ちが丸ごと消えます。

## なぜ semi-join ではなく SubPlan なのか

`EXISTS` と聞くと、結合（semi-join）に化けるのでは、と思うかもしれません。半分正解で、どこに書くかによります。

`EXISTS` を WHERE のトップレベル、つまり「この行を残すか捨てるか」のフィルタとして書いた場合、PostgreSQL はそれを結合（`SEMI JOIN`）へ書き換えられることがあります。こうなれば、ほかのテーブルと同じ土俵に乗るので、hash にするか並べ替えるか、どの順で処理するかを、プランナが自由に選べます。

ところが今回の `EXISTS` は、`CASE WHEN EXISTS(...) THEN 'EMPLOYEE' ... END` のように、SELECT 句で「種別という値を組み立てる」ために使っています。これは行を絞り込むフィルタではなく、行ごとに答えを計算する式の一部です。式の中の `EXISTS` は結合には書き換えられず、行を処理するたびに呼ばれる小さな問い合わせ、すなわち SubPlan として残ります。

つまり同じ `EXISTS` でも、WHERE で「残すか」を問うのか、SELECT で「値」を組み立てるのかで、実行のされ方がここまで変わります。今回 `EXPLAIN` に SubPlan が並んでいたのは、後者だったからです。`EXISTS` という式そのものの仕様は、公式ドキュメントにまとまっています。

https://www.postgresql.org/docs/current/functions-subquery.html

:::message
なお、`EXISTS` にしたついでに、この `unified_contract`（例の DISTINCT ON サブクエリ）を `LEFT JOIN` から `INNER JOIN` につなぎ直したくなりますが、これは禁物です。どうせ契約のある行しか数えないのだから、と `INNER` にした瞬間、プランナはこの「行数を 200 と読み違えているサブクエリ」を再び駆動表に選べるようになり、nested loop が戻ってきます。`LEFT JOIN` のままにして、在籍者テーブル（`worker`）を駆動表に固定しておくのが肝でした。
:::

結局のところ、結合で取ってきた列が、最終的に存在するかどうかの判定にしか使われていないなら、その結合は `EXISTS` に移せます。列を取り出すことと、存在を問うことは、プランナにとってまったく別物なのです。

# 実際、どれだけ速くなったか？

効き目を、改善の前後で実測しました。コミットを `git checkout` で3つの時点に巻き戻します。何も手を入れる前、DB集計＋並列化を入れた後、さらに `EXISTS` を入れた後、の3点です。それぞれで同じテナントに同じ集計を何度か実行して中央値を取れば、2段階の改善のどちらがどれだけ効いたかを切り分けられます。就業形態別のカードは、こうなりました。

| 計測点               | 中央値  | 直前比 |
| -------------------- | ------- | ------ |
| 改善前               | 7,306ms | —      |
| DB集計＋並列化を適用 | 1,841ms | ×4.0   |
| さらに EXISTS を適用 | 433ms   | ×4.3   |

DB集計＋並列化で 7.3秒が 1.8秒になり、さらに `EXISTS` で 0.43秒まで落ちました。外側の手当てとクエリの書き換えが、それぞれおよそ4倍ずつ効いて、合わせて約17倍です。ほかの集計カードもおおむね同じ傾向で、件数は全カード・全計測点でぴったり一致しています。プランの選び方を変えただけなので、結果は1件も動いていません。

# 巨大テナントでは、効き方が変わる

ここまでは在籍2,000人規模のテナントの話でした。全体で20万人を超えるような、桁違いに大きいテナントだと、同じ `EXISTS` のクエリでも、プランは少し違う顔を見せます。

ひとつは、SubPlan の中身です。2,000人規模では、従業員・役員・業務委託の判定はどれも、行ごとにインデックスを引く相関 SubPlan でした。ところが巨大テナントでは、役員と業務委託だけが hashed SubPlan、つまりテーブルを一度だけ丸ごと読んでハッシュ表に載せ、あとは照合するだけ、という形に変わっていました。従業員は相関 SubPlan のままです。

これは PostgreSQL が、SubPlan についてハッシュ版と相関版の両方を用意しておき、コストの安いほうを選ぶ alternative subplan という仕組みのためです。小さいテーブルは丸ごとハッシュ表に載せたほうが安く、行数の多い従業員はインデックスを引くほうが安くなります。規模に応じて、子プランごとに最適な形が違っていたわけです。

もうひとつは、`EXISTS` 化の効きそのものです。巨大テナントで改善前後の `Buffers`（触れた 8KB ページ数、つまり仕事量の目安）を比べると、8,320,552 から 4,082,926 へ、およそ2分の1にとどまりました。2,000人規模での14分の1とは、はっきり差があります。理由は次の節で詳しく見ますが、巨大テナントでは nested loop の病よりも、毎回これだけの母集団を組み立て直すこと自体のコストのほうが大きいからです。

# 構造的な限界はどこに見えたか

`EXISTS` でプランナの病は取り除けました。それでも、巨大テナントの改善後の `Buffers` は、まだ約408万ページあります（8KB ページなので、のべ約32GB 分のアクセスです）。内訳を見ると、その大半は種別の判定ではありませんでした。

- 個人の在籍履歴テーブルの引き当て：1行ずつの `Index Scan`（約167万 buffers）
- 就業情報の履歴テーブルの引き当て：同じく（約153万 buffers）
- 種別の `EXISTS` 判定：合わせても誤差レベル

つまり残った遅さの正体は種別の判定ではなく、そのテナントの在籍者ひとりひとりを毎リクエスト在籍履歴のテーブルで「いま有効か」判定して数え直していることでした。2,000人規模でも `DISTINCT ON` が毎回約17万行を畳んでいて（ソートがディスクへ溢れる外部マージソートになっていました）、根っこは同じです。

要するに、リクエストのたびに母集団を丸ごと組み立て直しているわけです。これは本質的に O(母集団のサイズ) で、インデックスは全部効いていても、母集団のぶんだけ探索が積み上がります。しかも全員を数える集計は、ほとんどの行が答えに効いてくる（インデックスで候補をふるい落とす余地が小さい）ので、ここから先はクエリチューニングでは大きく削れません。

これが、`EXPLAIN` の先に見えてきた構造的な限界でした。

## より大きくやるなら

サブ秒で安定させたいなら、毎リクエストで数え直すこと自体をやめるしかありません。鮮度とのトレードオフで、いくつか段階があります。

| 手段                                | 速さ                                  | 鮮度       | コスト       |
| ----------------------------------- | ------------------------------------- | ---------- | ------------ |
| 短期キャッシュ（TTL 数分）          | ほぼ ms（TTL 切れ時のみ再計算）       | 数分遅れ   | 軽（最有力） |
| 集計テーブル（イベント / 定期更新） | 常時 ms                               | 即時〜数分 | 中           |
| 現在の就業形態を列として持たせる    | 常時 ms（履歴テーブルとの結合が不要） | 即時       | 中〜大       |

ダッシュボードのカウントは毎秒変わる値ではないので、現実的な落としどころは短期キャッシュでしょう。複数のカードが同時にスキャンすることによるレプリカの負荷も、あわせて和らぎます。ただ、どれも鮮度の扱いや更新・キャッシュの基盤を伴うので、これはクエリを速くする話ではなく、毎回数えるのをやめるという別レイヤーの設計判断になります。今回はそこには踏み込まず、プランナの病を治して O(母集団のサイズ) の素の下限まで戻したところで、ひと区切りとしました。

# おわりに

集計の遅延を分解してみて、手元に残ったのは3つの学びでした。

1つ目は、遅さは遅そうな場所にいるとは限らないということ。重いクエリを見て真っ先に SQL を疑いましたが、まず効いたのは SQL の外側でした。全行を取ってきて数えるのをやめたことと、直列 `await` を並列にしたことです。クエリ本体の書き換えも同じくらい効きましたが、その前に呼ばれ方と転送量を見直すだけで桁が変わることもあります。

2つ目は、`EXPLAIN` の見積りと実測のギャップを読むこと。桁違いの誤推定の手前にはたいてい `DISTINCT` やサブクエリがいて、`rows=200`（`DEFAULT_NUM_DISTINCT`）は派生リレーションに統計がないというサインです。そこに結合をぶら下げると nested loop が牙を剥きます。列の取得を `EXISTS` の存在判定に変えれば誤推定のサブクエリを駆動表から外せますが、どんな場合も一発で速くなる魔法ではなく、効き幅もデータ規模で変わります。

3つ目は、プランナを直しても消えない遅さがあるということ。毎リクエスト O(母集団のサイズ) で数え直す構造はもうクエリチューニングの管轄外で、そこから先は数え直すのをやめるという設計の話になります。

もしインデックスも統計も妥当なのになぜか遅い場面に出くわしたら、まずは本当に遅いのがどこなのかを切り分けてみてください。呼ばれ方か、クエリ本体か、それとも設計か。そのうえで `EXPLAIN ANALYZE` の `rows` と `actual rows` のギャップを読み、その遅い結合は本当に列を取り出す必要があるのかを疑ってみる。
