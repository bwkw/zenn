# TL;DR

# はじめに

こんにちは、Dress Code でプロダクトエンジニアをしている [ないとー](https://x.com/_bwkw_) です！

最近はデータの履歴をどう扱うか考えたり、設計上の判断を ADR に書いたりしています。そのなかで気になっているのが、結果を残すことと、後からその判断を理解できることの違いです。

たとえば、申請に承認済みと残っていれば、次の担当者は仕事を進められます。でも、後から申請の対象外だったと分かったとき、その状態だけでは当時何を確認して承認したのか分かりません。設計も同じで、採用した方式が分かっていても、条件が変わったときに何を選び直せるかは、結論だけでは読み取れません。

この記事では、所属の訂正や申請の承認を例に、データの履歴と判断の理由を分けて考えます。そこから ADR や AI に先例を渡す話まで、日頃の設計を通じて私なりに考えていることを書いてみます。

# 正式な記録だけでは、過去の判断を説明できない

承認済みという状態を受け取れば、次の担当者は、承認者の検討をたどり直さずに仕事を進められます。ただし、実行者に権限があるか、実行時の条件を満たすかは別の確認です。前の工程の判断が済んでいるからと、その後の確認まですべて不要になるわけではありません。

営業部を対象とする申請を、4/5 に承認したとします。その後、4/1 付で開発部へ異動していたことが分かり、4/10 に人事の台帳へ登録されました。今の台帳で 4/5 の所属を調べると開発部なので、対象外の人を承認したように見えます。

この場合は、いったん済んだはずの対象者の確認を、後から調べ直すことになります。ただ、訂正後の所属を見ただけでは、当時の処理が何を使って承認したのかは分かりません。まずは、どの記録を基準にしたかと、いつの情報を使ったかを調べる必要があります。

所属が複数のシステムにある場合、後から更新された値が正式な異動を反映しているとは限りません。人事の台帳を正式な記録（System of Record、SoR）と決めるなら、連携先との食い違いは台帳を基準に調べ、誤りがあれば人事の手続きに沿って台帳を訂正します。SoR は、読む先を決めるだけでなく、訂正する先と、その責任を決める話でもあります。

もっとも、人事上の所属が営業部で、費用の配賦先が開発部でも、どちらかが誤っているわけではありません。二つの項目は違う業務のためにあります。同じ人物のデータだからと所属という一項目にまとめると、申請の対象判定に使うべき値まで曖昧になります。正式な記録を決める前に、何の記録なのかが揃っている必要があります。

## 当時把握していた情報を残す

参照先が人事の台帳だと分かっても、まだ当時の状況は確定しません。冒頭の異動は 4/10 に登録されたので、4/5 当日のシステムには旧部門が登録されていました。同じ台帳でも、今から振り返った所属と、当時把握していた所属は異なります。

Martin Fowler の Bitemporal History は、こうした問題を、情報が有効な時間と、その情報を記録した時間の二つで整理しています。遡って訂正される履歴と、何を知っていたかの履歴を分ける考え方です。

@[card](https://martinfowler.com/articles/bitemporal-history.html)

異動が有効になるのは 4/1、それをシステムが知るのは 4/10 です。

![登録後の正式な履歴では4/1から新部門だが、当時のシステムは4/10まで旧部門と認識していた](/images/decisions-data-and-context/two-times-short-dates.png)

ここでもう一つ分けるのが、実際の入力です。当日の台帳に旧部門が登録されていても、キャッシュや手動の指定を使った可能性があれば、その処理も旧部門を使ったとは断定できません。

| 知りたいこと | 答え |
| --- | --- |
| 今の記録から見た、4/5 の正式な所属 | 新部門 |
| 4/5 の時点で、システムが把握していた所属 | 旧部門 |
| 4/5 の処理が実際に使った所属 | 処理の入力や記録から確認する |

正式な所属を訂正しても、過去に行った処理が消えるわけではありません。当時の入力を説明する調査と、訂正後の所属で対象者を再判定する処理では、使う記録が違います。

だからといって、すべてのデータに二つの時間を持たせる必要はなく、Fowler もその複雑さを指摘しています。一回の処理の入力を知るだけなら、値と取得時点を保存する方法があります。任意の日付でシステムが何を把握していたか調べるなら、登録・訂正の履歴が必要になります。

## 履歴と判断の理由を分ける

当時の入力とは別に、申請に何が起きたかも記録から調べることになります。申請、承認、実行という変更の履歴があれば、どこまで処理が進んだかを追えます。

イベントソーシングは、状態の変更をイベントとして保存し、その列から状態を構成する設計です。承認されたイベントを適用して承認済みの状態を再構築することと、所属や規則を使って承認してよいか判断することは別です。結果をイベントとして残しているなら、再構築のたびに承認の判断までやり直す必要はありません。

Fowler の説明には、正式な記録を現在の状態とするか、イベントの列とするかという選択も登場します。SoR を考えることは、データを一つのデータベースへ集めることではありません。出来事の列を基準として状態を構成する設計もあります。

@[card](https://martinfowler.com/eaaDev/EventSourcing.html)

冒頭の申請なら、4/5 に承認した事実は、後から所属を訂正しても変わりません。訂正後の所属で判定すれば対象外になり得ますが、それは当時の状態の再構築ではなく、別の情報を使った再判定です。

| 処理 | 冒頭の申請で扱うこと |
| --- | --- |
| 状態を再構築する | 4/5 に承認されたイベントから、承認済みの状態を構成する |
| 判断をやり直す | 訂正後の所属で、申請が承認条件を満たすか再判定する |
| 実行済みの処理に対応する | すでに手続きを進めていれば、取消しや訂正が必要か決める |

状態の再構築は、現実を巻き戻すことでもありません。再判定で対象外になっても、送信済みのメールや外部で完了した手続きが取り消されるわけではなく、それぞれに対応が必要です。

さらに、申請が承認済みのままでも、その間に何も起きなかったとは限りません。別の担当者が承認の取消しを試み、権限不足で拒否されたとします。申請の状態は変わっていませんが、取消しを試みたことと、それをシステムが拒否したことには、調査の手がかりとして意味があります。

拒否を業務イベントとして残す設計もあります。ただ、状態を構成するイベント列にその試行を含めていなければ、そこからは辿れません。誰が何を試み、どんな結果になったかという操作の証跡や、認証・参照の記録には、状態の変化だけでは捉えられない場面を残す役割があります。何を調べるための記録なのかで、残す対象も変わります。

![申請・承認・実行のイベントの列と、承認の根拠として必要な情報](/images/decisions-data-and-context/events-and-reasons.png)

図のイベント列から、申請が承認されたことは分かります。ただ、営業部に所属していたから承認したのか、所属にかかわらず例外を認めたのかは分かりません。取消しを試みた担当者も、異動を知ったから取り消そうとしたのか、別の問題を見つけたのかは、操作の証跡だけでは分かりません。理由を一緒に残すことはできますが、出来事や操作の記録があるだけで、判断の理由まで説明できるわけではないんですよね。

# ADR に残した選択を、変更できない要件にしない

一件の申請についても、状態、操作、判断の理由はそれぞれ違う情報でした。その申請を処理する仕組みの設計にも、同じように、採用した方式だけでは分からない判断があります。

申請の実行処理を同期方式にしたとします。処理量が少なく、待ち時間も許容範囲だったので、構成の簡単さを優先した設計です。ところが ADR に非同期処理は不要とだけ残すと、後から読む人には、業務上そうする必要があるのか、当時の負荷なら不要だったのか区別できません。

処理量が増えたときに必要なのは、同期方式の是非をゼロから議論することではなく、何を維持する必要があり、何は選び直せるのかを調べることです。

![同期処理を選んだ結論だけでなく、処理量と待ち時間の前提、受け入れたリスク、見直す条件を残す](/images/decisions-data-and-context/decision-boundary.png)

Michael Nygard の Documenting Architecture Decisions でも、理由を理解せずに過去の決定を受け入れることと、理由を理解せずに覆すことの両方が問題として挙げられています。Nygard は、判断を置き換えた後も古い ADR を残し、置換先を示す書き方を紹介しています。過去の選択を尊重することと、同じ方式を使い続けることは別です。

@[card](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

ただ、理由が詳しく残っていることで、過去の判断を変えにくくなる可能性もあります。十分に比較して選ばれた設計だと分かると、その比較をやり直さないだけでなく、今も同じ設計を使ってよいと受け取ってしまうかもしれません。説明に納得できることが、現在の条件を調べる代わりになってしまう場合です。

たとえば、この ADR に非同期処理の監視や障害復旧の負担が詳しく書かれていても、それが当時の運用体制を前提にした評価なら、体制が変わった後まで同じ重みで比較できるとは限りません。記録された説明を否定しなくても、今なら別の方式を選ぶ余地はあります。理由を理解するのは過去の選択を守るためだけではなく、どの条件が変われば選び直せるかを知るためでもあります。

## 選択肢を狭めた制約を残す

結果の確定を待たないと次の業務へ進めないなら、受付だけ返して後から完了を知らせる設計は、そのままでは採用できません。一方、結果をその場で返すことが、内部の処理まで同期方式にすることを意味するとは限りません。業務が求める条件と、その条件を満たすために選んだ実装は別です。

同じ ADR に書かれていても、次の三つは変更の仕方が違います。

| 判断に含まれるもの | 例 | 見直す際の検討 |
| --- | --- | --- |
| 満たす必要がある制約 | 結果の確定を待たないと次の業務へ進めない | 業務の進め方を変えられるか |
| 選択の際に優先したこと | 構成を簡単に保ち、運用の負担を抑える | 複雑さと引き換えに何を得られるか |
| 未検証の仮定 | 今後も処理量は大きく増えない | 見込みが現在も妥当か |

制約にも理由があります。外部の仕組みが対応していないのか、契約で認められていないのか、運用する人や時間が足りないのかで、相談する相手も変わります。当時の体制では運用できなかった方式なら、技術の比較だけでなく、体制を変えることで候補に戻せるかもしれません。方式の比較表だけでは見えない選択肢です。

## 実装と前提をそれぞれ確かめる

表にある処理量の見込みも、測定で確認した結果とは違います。想定した負荷で測ったのか、利用者数から見積もったのかで、選択の根拠は変わります。後から分かったことを当時から知っていたように書き直すと、どこまで分かったうえで選んだ設計なのかが失われます。

たとえば、待ち時間が許容範囲を超えたとき、当時から測定条件が実態に合っていなかったのか、その後に利用状況が変わったのかでは、振り返る内容が違います。前者なら検証の仕方を、後者なら条件の変化を調べることになります。今の性能だけで当時の選択を評価すると、この違いまで消えてしまいます。

前提の確認と、決めた方式が実装されているかの確認も別です。[MADR の公開版 4.0.0 のテンプレート](https://github.com/adr/madr/blob/4.0.0/template/adr-template.md) には、任意の項目として Confirmation があります。決めたことが実装されているかを、どう確認するかを書く欄で、[この見出しを採用した ADR](https://adr.github.io/madr/decisions/0018-use-confirmation-as-heading.html) でも、決定そのものの妥当性とは区別されています。

同期処理の例なら、確認する対象と手段は次のように分かれます。

| 確認する対象 | 手段の例 |
| --- | --- |
| 決めた方式で実装されているか | コードの確認やテスト |
| 実際の待ち時間が許容範囲に収まるか | 運用時の計測 |
| 想定していた処理量や業務上の条件が変わっていないか | 利用状況や要件の確認 |

待ち時間を見直す条件として書いても、その変化を誰も確認していなければ、設計は見直されないままです。また、許容範囲を超えたことだけで、次の方式が非同期処理に決まるわけでもありません。結果をその場で返す制約を保って内部の処理を変えるのか、受付と完了を分けられるよう業務を変えるのか。見直す条件は、当時の選択を再検討するきっかけであって、次の答えではありません。

# 記録と一緒に、見直す仕事を引き継ぐ

ここまでで、同期方式を選んだ理由と、見直す条件は分かりました。次の設計者は当時の比較を参考にできますが、現在のコードのどこを変えるかは、実装と業務を調べないと決まりません。ADR を読むことで省略できる検討と、今の設計者が引き受ける検討が、ここで分かれます。

設計図が残っている建物でも、改修するなら現在の用途や過去の改修、その場で見つかった問題を調べます。図面は調査を助けますが、その建物を今どう使うかまでは決めてくれません。ADR も、当時の説明を現在のコードや要求に照らし合わせて読むものだと思っています。

Peter Naur の 1985 年の論文 Programming as Theory Building は、プログラミングを、現実の問題とプログラムがどう対応しているかを理解していく仕事として捉えています。構造の理由を説明し、新しい要求に応じて変更できることも、その理解に含まれます。記録を渡すだけで、その理解まで引き継げるわけではありません。

https://gwern.net/doc/cs/algorithm/1985-naur.pdf

引き継ぐ側に議論のログをすべて読ませるのも、別の負担をかけます。採用しなかった案や途中で捨てた前提から、最終的な設計の理由を探さなければなりません。Parnas と Clements の 1986 年の論文 A Rational Design Process: How and Why to Fake It は、実際の設計には発見や手戻りがある一方、文書には設計をレビューし、引き継げるよう整理する役割があると論じています。

https://www.laputan.org/pub/papers/Fake.pdf

測定結果へのリンクがあっても、当時の構成が分からなければ、今の環境でも同じ結果になるかは判断できません。規則へのリンクも、最新版に更新されていれば、過去の申請に適用した条件を辿れなくなります。根拠へのリンクを置くことと、後から判断を確かめられることは、必ずしも同じではありません。

変化の伝わり方も一様ではありません。処理量の増加は計測で分かっても、契約上の制限が外れたことは、契約を扱う人が知っているだけかもしれません。設計を考える人に伝わらなければ、以前は採用できなかった方式が、候補に戻ることもありません。ADR の文章を充実させるだけでは、この連絡までは生まれないんですよね。

## AI に先例を渡す場合

記録から判断するのが AI になっても、当時の条件を確かめる必要は変わりません。冒頭の申請に戻ると、仮に所属の条件を満たさなくても、一度だけ例外として承認していた可能性があります。理由が残っていなければ、その記録だけでは通常の承認と区別できません。

![結論が参照される期間は、それを支えた前提が成立する期間より長くなることがある](/images/decisions-data-and-context/decision-lifetime-review.png)

投資会社 Foundation Capital が提案する Context Graphs も、承認の結果だけでなく、どの規則を使い、何を参照し、誰が例外を認めたかを、後から調べられる記録にしようとするものです。同社の記事では、人の頭の中にあった理由を直接記録できるわけではなく、行動の記録を積み重ね、そこから理由を推測するという説明がされています。

@[card](https://foundationcapital.com/ideas/context-graphs-one-month-in)

ここで気になるのは、後から推測した理由が、当時の判断の理由として扱われることです。AI が過去の承認に筋の通った説明を付けても、それだけで承認者がその説明に沿って判断したとは分かりません。その説明を次の先例の根拠に使えば、記録から確かめたことではなく、後から付けた説明が判断を支えることになります。

これは、ADR を後から整える場合にも起こり得ます。今なら説明できる理由を、当時から分かっていた理由のように書くと、見込みで決めた部分まで検証済みのように見えてしまいます。当時の記録と、後から得た理解の両方には価値がありますが、それぞれが答えられる問いは違います。

また、先例に制約が書かれていない場合も、制約がなかったのか、単に記録されなかったのかは分かりません。先例を根拠に今回の確認を省略すると、その空白まで、確認不要という判断に変わってしまいます。検索によって先例を探す手間は省けても、今回の条件に使えるかを判断する仕事は残ります。

# おわりに

DRESS CODE で私がデータの扱いを考えるときに気になるのは、一つの値が、参照する業務では判断の根拠になることです。所属の項目なら、何の所属で、いつの情報なのかが曖昧なままでは、業務ごとに違う解釈が入り得ます。

最近、私が書く ADR には、決定だけでなく受け入れるリスクや見直す条件も残しています。こうした記録を次の設計に使うとき、当時の比較を毎回繰り返す必要はなくても、前提まで調べなくてよいことにはなりません。何を維持する必要があり、どの条件なら選び直せるかが、その区別の手がかりになります。

判断を引き継ぐことは、答えだけでなく、次の人がどこまで考えなくてよいかを引き継ぐことでもあります。承認済みだからと実行時の権限まで確認不要にはならず、詳しい ADR があるからと今の負荷まで検討不要にはなりません。過去の検討を使える範囲と、今の条件で考え直す範囲が分かれば、以前の判断を尊重しながら別の答えを選べます。記録を設計するときには、この境目まで含めて考える必要があると思っています。

データや ADR に何を残すか考えるときの参考になれば幸いです👋
