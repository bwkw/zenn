# TL;DR

- 過去の判断を引き継げれば、次の人は同じ検討を繰り返さずに仕事を進められる。ただし **結論を使える範囲**まで分からないと、条件が変わっても使い続けてしまう。
- データの履歴から何が起きたかは調べられるが、**なぜそう判断したか**まで分かるとは限らない。
- ADR では、選んだ理由のうち**守るべき条件・優先したこと・まだ確かめていない前提**を区別する。要件を満たすために必要だったことと、当時の判断で選んだことを分ければ、条件が変わったときに見直す箇所が分かる。
- すべての経緯を保存する必要はない。次の人や AI が過去の結論を使うために、**何をそのまま引き継ぎ、どこから考え直すか**が分かる記録にする。

![データの履歴と判断の理由を分けて考える記事の要約](/images/decisions-data-and-context/tldr.png)

# はじめに

こんにちは、Dress Code でプロダクトエンジニアをしている [ないとー](https://x.com/_bwkw_) です！

最近はデータの履歴をどう扱うか考えたり、設計上の判断を ADR に書いたりしています。結果が残っていても、後からその判断の理由まで理解できるとは限りません。

たとえば申請に承認済みと残っていれば、次の担当者は仕事を進められます。でも後から申請の対象外だったと分かったとき、その状態だけでは当時何を確認して承認したのか分かりません。設計でも採用した方式が分かるだけでは、条件が変わったときに何を選び直せるかまでは読み取れません。

この記事では、営業部向けソフトウェアの利用申請とアカウント発行を例に、データの履歴と判断の理由を分けて考えます。そこから ADR や AI に先例を渡す話まで、日頃の設計を通じて私なりに考えていることを書いてみます。

# 正式な記録だけでは、過去の判断を説明できない

原則として営業部の人だけが利用できるソフトウェアがあるとします。利用申請が承認されれば、次の担当者は対象者の審査を最初からやり直さずに、アカウントの発行へ進めます。ただし、発行する担当者に権限があるか、利用可能なライセンスが残っているかは別の確認です。承認が済んだことによって、省略できる検討の範囲があるわけです。

この利用申請を 4/5 に承認し、アカウントも発行したとします。その後、申請者が 4/1 付で開発部へ異動していたことが分かり、4/10 に人事の台帳へ登録されました。今の台帳で 4/5 の所属を調べると開発部なので、対象外の人の利用を認めたように見えます。

訂正後の所属を見ただけでは、当時何を使って承認したのかは分かりません。どの記録を基準にしたかと、いつの情報を使ったかを調べる必要があります。

所属が複数のシステムにある場合、後から更新された値が正式な異動を反映しているとは限りません。人事の台帳を正式な記録（System of Record、SoR）と決めるなら、連携先との食い違いは台帳を基準に調べます。台帳に誤りがあれば人事の手続きに沿って訂正します。SoR を決める際には、誤りを直す場所と訂正を担う人も決めます。

もっとも、人事上の所属が営業部で、ソフトウェアの費用の配賦先が開発部でも、誤りとは限りません。この申請が条件にするのは人事上の所属なので、費用の配賦先では代用できません。

## 当時把握していた情報を残す

ただ、今の台帳と 4/5 当日の台帳では、所属が違います。異動が登録されたのは 4/10 なので、承認した時点では旧部門が登録されていました。

Martin Fowler の Bitemporal History は、情報が有効な時間と記録した時間の二つでこうした問題を整理しています。遡って訂正される履歴と、何を知っていたかの履歴を分ける考え方です。

@[card](https://martinfowler.com/articles/bitemporal-history.html)

![登録後の正式な履歴では4/1から新部門だが、当時のシステムは4/10まで旧部門と認識していた](/images/decisions-data-and-context/two-times-short-dates.png)

台帳に登録されていた値と処理に使った値も区別します。4/5 の台帳に旧部門が登録されていても、承認時にその値を使ったかは別に確かめる必要があります。

| 知りたいこと | 答え |
| --- | --- |
| 今の記録から見た、4/5 の正式な所属 | 新部門 |
| 4/5 の時点で、システムが把握していた所属 | 旧部門 |
| 4/5 の処理が実際に使った所属 | 処理の入力や記録から確認する |

だからといって、すべてのデータに二つの時間を持たせる必要はなく、Fowler もその複雑さを指摘しています。一回の承認に使った所属を知るだけなら、その値と取得時点を承認の記録に残す方法があります。任意の日付でシステムが何を把握していたか調べるなら、登録・訂正の履歴が必要になります。残す範囲は、後から答えたい問いで変わります。

保存や更新にもコストがかかるので、何でも詳しく残せばよいわけではありません。ただ、取り消しにくい処理や他の担当者が先例として使う判断では、根拠を辿れない影響が大きくなります。記録を残さない場合の影響と、維持する負担を比べて必要な範囲を絞ります。

過去の申請について入力の記録がない場合は、当時の台帳から候補を絞ることはできても、実際に使った値まで確定できるとは限りません。その場合は入力を確かめられなかったことを残し、現在の利用条件に照らして、継続利用を認めるかを判断することになります。当時の承認を説明できないことと、今の対応を決められないことは別です。

## 履歴と判断の理由を分ける

申請、承認、アカウント発行の履歴からは、どこまで処理が進んだかを調べられます。

イベントソーシングは、状態の変更をイベントとして保存し、その列から状態を構成する設計です。承認されたイベントを適用して承認済みの状態を再構築することと、所属や規則を使って承認してよいか判断することは別です。結果をイベントとして残しているなら、再構築のたびに承認の判断までやり直す必要はありません。

@[card](https://martinfowler.com/eaaDev/EventSourcing.html)

冒頭の申請なら、4/5 に承認した事実は、後から所属を訂正しても変わりません。再構築、再判定、その後の対応は、それぞれ別の処理です。

| 処理 | 冒頭の申請で扱うこと |
| --- | --- |
| 状態を再構築する | 4/5 に承認されたイベントから、承認済みの状態を構成する |
| 現在の継続利用を判断する | 訂正後の所属と利用条件を使って、継続利用を認めるか判断する |
| 実行済みの処理に対応する | 利用を認めないなら、発行済みアカウントの停止や権限回収を進める |

再判定で対象外になっても、外部サービスに発行したアカウントが消えるわけではありません。停止や権限回収は別に実行し、その結果を新しく記録する必要があります。

利用情報を参照しただけなら、申請の状態は変わりません。権限不足で変更を拒否した場合も同じですが、誰が何を試みたかは調査に必要なことがあります。こうした事象を業務のイベント列に含めるか、操作やアクセスの証跡として別に残すかは、調べたい内容に応じて決めます。

![申請・承認・アカウント発行という実行の履歴と、承認の根拠として必要な情報](/images/decisions-data-and-context/events-and-reasons.png)

図のイベント列から、申請が承認されたことは分かります。ただ、営業部に所属していたから承認したのか、所属にかかわらず例外を認めたのかは分かりません。

この違いを後から調べるには、承認時に参照した所属と適用した利用条件が手がかりになります。例外の承認なら、誰がどの条件の例外を認め、なぜ認めたのかを残します。思考の過程をすべて保存しなくても、通常の承認と例外の承認を区別するための情報は残せます。

異動を把握したうえで、営業案件の引き継ぎが終わるまで利用を認める例外も考えられます。その承認なら、引き継ぎが終わった時点で利用を続けてよいか確かめることになります。承認済みという状態だけでは、いつ確認が必要になるのか分かりません。

# ADR に残した選択を、変更できない要件にしない

利用条件を確認する承認と、複数の方式から選ぶ設計判断では、結論の出し方が違います。共通するのは、当時の条件を辿れれば見直す箇所を絞れることです。設計上の判断を残す ADR は、その手がかりになります。

このアカウント発行を同期方式で設計したとします。処理量が少なく待ち時間も許容範囲だったため、構成の簡単さを優先した選択です。ところが ADR に非同期処理は不要とだけ残すと、業務上そうする必要があるのか、当時の負荷なら不要だったのかを後から読む人は区別できません。

![同期処理を選んだ結論だけでなく、処理量と待ち時間の前提、受け入れたリスク、見直す条件を残す](/images/decisions-data-and-context/decision-boundary.png)

Michael Nygard の Documenting Architecture Decisions でも、理由を理解せずに過去の決定を受け入れることと、理由を理解せずに覆すことの両方が問題として挙げられています。過去の選択を尊重することと、同じ方式を使い続けることは別です。

@[card](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

ただ、過去の説明に納得すると現在の条件を調べずに済ませてしまう場合もあります。非同期処理の監視や障害復旧の負担を理由に同期方式を選んでいても、運用体制が変われば別の方式を選ぶ余地はあります。

## 選択肢を狭めた制約を残す

アカウントの発行完了を確認してから利用者へ案内する業務なら、受付済みを発行完了として扱うことはできません。一方、完了を確認してから案内することが、内部の処理まで同期方式にすることを意味するとは限りません。非同期で発行し、完了を確認した後に案内する設計でも、この条件は満たせます。業務が求める条件と、その条件を満たすために選んだ実装は別です。

判断の理由を読むときは、守るべき条件と優先したこと、まだ確かめていない前提を区別します。何を守って設計を変えるのか、何から確かめ直すのかが違うためです。

| 判断に含まれるもの | 例 | 見直す際の検討 |
| --- | --- | --- |
| 守るべき条件 | 発行完了を確認してから利用者へ案内する | 条件を満たせる実装はほかにあるか |
| 優先したこと | 構成を簡単に保ち、運用の負担を抑える | 今も運用の負担を抑えることを優先するか |
| まだ確かめていない前提 | 今後も処理量は大きく増えない | 利用状況は見込みと合っているか |

制約にも理由があります。外部の仕組みが対応していないのか、契約で認められていないのか、運用する人や時間が足りないのかで、相談する相手も変わります。当時の体制では運用できなかった方式なら、技術の比較だけでなく、体制を変えることで候補に戻せるかもしれません。方式の比較表だけでは見えない選択肢です。

## 実装と前提をそれぞれ確かめる

現在の負荷で測定した結果と、将来の処理量の見込みも区別します。今は十分に速くても、処理量が増えた後まで同じ待ち時間に収まるとは限りません。

待ち時間が許容範囲を超えたら、当時の測定条件と現在の構成や負荷を比べます。初めから想定が実態とずれていたのか、運用を始めてから条件が変わったのかが分かれば、追加で測る範囲や設計を見直す箇所を絞れます。

前提の確認と決めた方式が実装されているかの確認も別です。[MADR の公開版 4.0.0 のテンプレート](https://github.com/adr/madr/blob/4.0.0/template/adr-template.md) には任意の項目として Confirmation があります。決めたことが実装されているかをどう確認するかを書く欄です。[この見出しを採用した ADR](https://adr.github.io/madr/decisions/0018-use-confirmation-as-heading.html) でも、決定そのものの妥当性とは区別されています。

アカウント発行の例なら、確認する対象と手段は次のように分かれます。

| 確認する対象 | 手段の例 |
| --- | --- |
| 決めた方式で実装されているか | コードの確認やテスト |
| 実際の待ち時間が許容範囲に収まるか | 運用時の計測 |
| 想定していた処理量や業務上の条件が変わっていないか | 利用状況や要件の確認 |

待ち時間が許容範囲を超えても、非同期処理への変更が自動的に決まるわけではありません。見直す条件は、再検討を始める手がかりであって、次の答えではありません。

# 記録と一緒に、見直す仕事を引き継ぐ

次の設計者は当時の比較を参考にできますが、現在のコードのどこを変えるかは、実装と業務を調べないと決まりません。設計図が残っている建物でも、改修するなら現在の用途や過去の改修、その場で見つかった問題を調べます。ADR も、当時の説明を現在のコードや要求に照らし合わせて読むものだと思っています。

Peter Naur の 1985 年の論文 Programming as Theory Building は、プログラミングを、現実の問題とプログラムがどう対応しているかを理解していく仕事として捉えています。構造の理由を説明し、新しい要求に応じて変更できることも、その理解に含まれます。記録を渡すだけで、その理解まで引き継げるわけではありません。

https://gwern.net/doc/cs/algorithm/1985-naur.pdf

後任に議論のログをすべて読んでもらうのも負担がかかります。採用しなかった案や途中で捨てた前提が混ざった議論から、最終的な設計の理由を探さなければなりません。Parnas と Clements の 1986 年の論文 A Rational Design Process: How and Why to Fake It は、実際の設計には発見や手戻りがある一方、文書には設計をレビューし、引き継げるよう整理する役割があると論じています。

https://www.laputan.org/pub/papers/Fake.pdf

発行処理の設計を引き継ぐなら、同期にした理由と、比較に使った処理量や待ち時間を ADR にまとめ、詳しい測定や議論へ参照を置く形が考えられます。読む人は判断の要点を先に掴み、必要な箇所だけ詳しく調べられます。待ち時間を比較するなら、測定時の構成や負荷も結果と一緒に辿れると、今の環境との違いを確かめられます。

見直す条件を残しても、その変化に誰も気づかなければ、過去の結論は使われ続けます。
処理量や待ち時間を誰が確認し、条件が変わったときに誰が再検討を始めるかも、引き継いでおきます。

## AI に先例を渡す場合

たとえば AI が、営業部から異動した人にも利用を認めた記録を見つけたとします。その承認は案件の引き継ぎが終わるまでの例外でした。別の異動者から利用申請があったなら、以前にも認めたというだけで承認せず、今回も例外を認める理由があるか、いつまで利用が必要かを現在の利用条件に照らして確かめます。

![結論が参照される期間は、それを支えた前提が成立する期間より長くなることがある](/images/decisions-data-and-context/decision-lifetime-review.png)

投資会社 Foundation Capital が提案する Context Graphs も、承認に使った規則や参照した情報、例外を認めた人まで後から調べられる記録にしようとするものです。同社の記事では、人の頭の中にあった理由を直接記録するのではなく、積み重ねた行動の記録から推測すると説明されています。

@[card](https://foundationcapital.com/ideas/context-graphs-one-month-in)

別の承認記録に理由が書かれておらず、AI が案件の引き継ぎのためだったと推測したとします。承認者が実際にそう考えていたかは、元の記録を読むだけでは分かりません。推測を当時の理由として保存してしまうと、次に読む人や AI は、その説明を根拠に別の申請を承認してしまうかもしれません。

後から得た説明を当時の根拠と取り違えることは、ADR の整理でも起こります。たとえば測定せずに同期方式を選び、運用を始めてから十分に速いと確かめたなら、その結果は決定時には知らなかったものです。説明を書き直すときも、当時の見込みと後の確認を分けて残せば、何を確かめずに決めたかが分かります。

設計の説明を後から整理する場合も、決定時の見込みと、その後に得た事実の区別は保ちます。
読みやすくまとめることと、当時すでに根拠が揃っていたように書くことは別です。

理由や期限のない記録も、似た申請を調べる手がかりにはなります。ただ、書かれていないから期限なしで使えた、とまでは判断できません。AI が補った理由は調査の仮説として扱い、当時の記録から分かったことと分けておきます。

# おわりに

最近、私が書く ADR には、決定とその理由に加えて受け入れるリスクや見直す条件も残しています。後から読む人が、その選択を今も使えるのか、どの条件が変わったら考え直すのかを判断できるようにするためです。

過去の判断を使えば同じ検討を繰り返さずに済みますが、条件が変わったところは考え直す必要があります。何が起きたかと、何を根拠に決めたかが分かる記録なら、次の人も過去の結論を使える範囲を確かめながら仕事を進められます。

データや ADR に何を残すか考えるときの参考になれば幸いです👋
